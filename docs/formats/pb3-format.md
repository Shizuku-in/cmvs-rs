# PB3B 图像

布局及地址依据来自[Amatsutsumi 样本](../games/amatsutsumi/README.md#样本身份)，其他引擎版本按各自档案选择。

当前实现 type 1（24/32 位）、type 2/3（JBP1）、type 5（32 位通道差分）、type 7（交错 BGRA LZSS）与带资源上下文的 type 6/8（参考底图上的块替换）。type 4 与其他 codec 仍明确报未支持；各类型边界和验证范围见下文。
参考固定 MIT 提交 a6bc9501d82264e228943f894af1b969ab98bee5 的 PB3B.cpp、CPB.cpp，
结合上述样本的 0x140036ae0、0x1400a0230 进行核对。

签名为 PB3B。头部 8..52 共 44 字节先与文件末尾 -3/-2 的两个字节交替 XOR，
再逐字节减去文件长度 -47 起的 44 字节（u8 wrapping）。
密钥取样区可以属于实际压缩数据，不把最后 47 字节另行剥离或当作校验和。
研究实现要求文件至少 99 字节，确保取样区不与变换头部重叠，输入最多 64 MiB。

| 解码后头部偏移 | 类型 | 用途 |
|---|---|---|
| 8 | u32 | 原始 field08，保留值，不推测业务含义 |
| 24 | u32 | type 1 方块边长，必须非零 |
| 28 | u16 | codec 类型 |
| 30 / 32 | u16 / u16 | 宽 / 高 |
| 34 | u16 | 位深 24 或 32 |
| 44 / 48 | u32 / u32 | 标记块区域 / 压缩字节区域的起点 |

图像尺寸必须非零，最终 RGBA 最多 64 MiB。以下区域布局描述 type 1：两区域起点不得指入变换头部。
每区域首先是每通道一个 u32 长度的表，其后按 B、G、R、可选 A 顺序连接各通道块。
长度加法检查溢出，所有块必须落在输入内，标记区域不得重叠压缩区域。

每个标记块有三个 u32：分块标记字节数、常量块数量、LZSS 解压后字节数。
接着是分块标记、每个常量块的一个值、LZSS 标记流。
LZSS 数据流来自另一区域的对应通道块。标记按高位先行：1 为引用、0 为字面字节。
使用 2048 字节零初始化窗口，写入位置从 2014 开始；引用为小端 u16，
位置 `word >> 5`，长度 `(word & 31) + 3`，支持重叠与环绕。
不能复用 PS2A 的标记位序、写入起点或长度规则。

图像按块行优先、自顶向下处理，右/下边缘按实际剩余尺寸截取。
分块标记 1 表示以一个值填充整块，0 表示逐像素读取 LZSS 输出。
24 位补 alpha=255，最终把 BGR(A) 转为顶向下 RGBA。

研究实现明确拒绝：引用越过声明输出、标记或字节流截断、块值耗尽、未消费的块值、
多余的 LZSS 流字节、分块标记数与尺寸不符、单通道解压长度超过像素数量。
原版对坏数据的无界指针行为和全局字典旧内容不予模拟；这些限制不是对所有历史 PB3 变体的兼容承诺。
没有核对 PB3 校验和，也不把 CPZ6 解密后的结构解析描述为真实性校验。

`cmvs-pb3 <文件>` 输出结构元数据，可识别但不会假装解码未支持类型。
`--rgba <新文件>` 只在完整解码成功后创建输出并拒绝覆盖，不按图像内字段拼接写入路径。
默认核心不增加第三方依赖。

`raster::RgbaImage` 检查尺寸和字节长度，预览合成保留目标 letterbox，最近邻比例适配，
每通道按 `(src*a + dst*(255-a) + 127)/255` 计算。它只定义资源预览，不声明已匹配 CMVS 图层混合。

## type 3：JBP1

参考 MIT 固定提交 a6bc9501 的 PB3B.cpp（type 2/3 共用 Decode3）与 JBP1.cpp 作格式定位，未复制源码，常数与运算宽度以本作二进制为准。

- 分发：`0x140036ae0` 对 type 2/3 调用 `0x1400a0700`。它以 `0x1400b4020` 解码文件偏移 52 起的 JBP1 流，得到宽高各向上对齐到 16 的 32 位缓冲；宽度不是 16 的倍数时按行把 BGR 裁回 PB3 宽度；24 位 alpha 全部置 255，32 位从 PB3 头 +44 偏移读取 alpha 游程：0x00/0xff 后跟 1 字节重复次数，其他字节为单个值，原版不在最后一个像素处截断游程。type 2 与 type 3 使用同一路径，具体样本验证见下文。

- JBP1 头（`0x1400a0ad0`）：`JBP1`；+4 表偏移（真实样本 44，PB3 内直接使用，不像 CMV6 再加 4）；+8 flags，bit 28–29 为子采样模式，模式 1（4:2:0，16×16 MCU）时宽高按 16 对齐；+16/+18 宽高（未对齐，须等于 PB3 头）；+20 位深 24；+28/+32 DC/AC 流字节数。本作 188 个样本 flags 均为 `0x58c00002`（另含 bit 27 显式量化表），Rust 只接受这一取值。

- 表区：16×u32 DC 频率、16×u32 AC 频率、16 字节零游程表（使用时 +1）、64 字节亮度与 64 字节色度量化表（自然序），其后紧接 DC 流与 AC 流；没有 JBPD 的纹理块布局与复用掩码。真实样本中 52 + 44 + 272 + DC + AC 恰为文件长度。

- 熵解码与 JBPD 相同（共用 `jbpd::Bits`/`Tree`）：位按 32 位字低位先取；频率树（`0x1400b3b40`）每次合并权重最小的两节点、序号小者优先并作 0 分支，排除 ≥ 2099999999 的权重；先解出全部 6 × MCU 数个 DC 差分并在整幅图累积（只用低 16 位）；每个 MCU 依次 4 个 Y、Cb、Cr 块，AC 符号 15 结束、0 读一元零游程选择器，其余按 `0x1400e4730`（即 JBPD zigzag 的第 1–63 项）写入未反量化的系数。

- IDCT（`0x1400b3c80`，以反汇编为准；反编译输出的若干 `__int16` 类型有误）：先按列，系数与量化值做 32 位乘积；某列第 1–7 行全零时整列填入第 0 行乘积的低 16 位；否则以常数 35467、50159、-121094、77062、-25570、-128553、-167963、-58980、98390、201373、134553、19571 做 `imul r32` 与 `sar 16`，全部 32 位回绕，仅写回截断为 16 位。再按行做同样的蝶形，结果 `sar 3` 后截断为 16 位。没有舍入偏置与电平偏移。

- 色彩：与 JBPD 相同的 91888、22544、46784、116112（32 位 `imul` 后 `sar 16`），亮度 + 384 加色度项作为 `0x1400e47b0` 768 字节表的下标：[0,256) → 0、[256,512) → 下标 - 256、[512,768) → 255，即 +128 后截断。下标越界时原版读取相邻数据，Rust 报错。色度 2×2 最近邻，输出 B、G、R。

`jbp1::decode` 输出对齐后的 BGR，`pb3::decode` 对 type 2/3 裁剪、补 alpha 并转为顶向下 RGBA。研究上限、流范围、频率溢出、零游程越界、截断表越界、JBP1 与 PB3 尺寸不符、alpha 游程越过最后像素均显式报错。

验证：188 个真实 type 3 可解码，13 个选定输出的完整 RGBA 与独立 Python 对照一致，覆盖宽度裁剪和高度填充；样本中的 32 位 alpha 游程由合成输入另行验证。合成回归还覆盖 IDCT、零游程、颜色 / alpha、裁剪、截断和非法布局。

## type 5/6：底图与局部替换

type 6/8 通过同一资源来源读取参考底图，type 7 则独立解码交错字节流，见下文。

type 5：32 位 BGRA。文件 52..84 为四组 (u32 标记偏移, u32 数据偏移)，均相对文件偏移 84。每通道独立解压 width×height 个差分字节，LZSS 与 type 1 共用 2048 字节窗口、写位置 2014、高位先取、0 字面/1 引用、位置 word>>5 和长度 (word&31)+3。字典存差分值，再以初值 0 对各通道作 u8 回绕累计，跨行继续、不在行首重置。输出 B/R 对换为 RGBA。

type 6 引用：文件 52..84 与四个小端 u32 密钥 `9cf375a6 a37869c5 794fa53e c73afe59` 循环 XOR，取首个 NUL 前的原始名称字节，追加 `.pb3`。拒绝空名和 32 字节内无 NUL，不猜测 Unicode。原版设缓存提示后经相同资源来源递归解码底图，并非只接受 type 5；Rust 使用同一 ImageSource/十个注册槽，也支持嵌套 type 6。底图缺失、不支持或尺寸不符均报错，不填空白图。

type 6 数据：变换后头 +12 为标记起点减 32（本次样本为 52，即文件 84）；+44 为标记起点至压缩数据的距离；+24 为解压 patch 字节数，不是块边长。以同一 LZSS 展开 patch。patch +0 的 u32 为掩码字节数，+4 尚无使用证据，掩码从 +8 起，像素从 +8+掩码长度起。按 8×8 块行优先，掩码高位先取、跨行连续：1 保留底图；0 按块内行优先读取 BGRA 并完全替换所有通道，不相加或作 alpha 合成。右/下边缘按实际剩余宽高裁切。当前要求 32 位且底图同尺寸，避免原版无界写入。

types 5/6 只提供流起点，按声明输出长度停止；尾部密钥取样区可能仍为压缩数据，不剥离。type 1 原有精确消费检查保留。偏移加法检查溢出，拒绝输出超限、引用越界、截断流、掩码与块数不符、替换像素不足/多余及 patch 大于完整图像+掩码+8。窗口整体零初始化，不模拟原版未初始化的尾部字节。

`pb3::decode` 支持独立 types 1/2/3/5/7；type 6/8 用 `decode_with_base` 提供底图，或 `image::load` 提供来源。场景、消息窗口和遮罩公共加载接入后者；独立 CLI/单文件预览仍明确要求参考上下文，不猜底图路径。参考链拒绝循环、超过 16 个活动文件、累计原始长度与 RGBA 声明长度超过 128 MiB；单文件/单图分别仍限 64 MiB，在解码分配前检查。这不是整个进程峰值内存限制。自定义 ImageSource 须显式接受参考读取的缓存提示。

原始字节缓存：ImageRead 持有原始字节和延迟提交 token；读取先消费提示、查询缓存，递归解码结束后才提交外层原始文件，解码失败也提交，符合 `0x140036820`。因此底图先于外层插入；命中只在读取时提升。直接 raw read API 仍在返回前提交。原始字节缓存不保存 RGBA；可选解码缓存由图像来源另行管理。

验证：23 个选定 type 5/6 输出（3 个 type 5、20 个 type 6）与独立 Python 对照一致，覆盖递归底图及不同尺寸，不代表全包逐项解码。合成回归覆盖差分、块边缘、偏移、循环引用、容量、缓存顺序和失败时保留旧 VM 状态。

## Type 2：复用JBP1路径

[Aoitori](../games/aoitori/README.md) 的 `bg300c2.pb3` 为1280×1024、32位type 2，JBP1 flags仍为 `0x58c00002`。只读核对该档案x64：`0x14003b0b0` 的case 2/3共同调用 `0x1400a76f0`，再经 `0x1400bb010` 解码JBP1；裁剪、24位补alpha及32位alpha游程与既有路径相同。type 2/3 共用解码分派、熵解码、IDCT、颜色转换和参考图像流程。仍只接受已验证的JBP1 flags。

选定 32 位样本的全部 alpha 与独立解析一致；该项不代表全部 RGB 像素的独立对照。共享 type 2/3 合成回归覆盖裁剪、位深、alpha 游程及截断。

## Type 7/8：旧版交错图像

[HASSAKU 构建](../games/hassaku/README.md#pb3-type-78) x64 的 `0x14002f3d0` 将 type 7 交给 `0x140091f00`：偏移 52/56 分别是相对 60 的 LZSS 标记与字节流起点，输出恰为宽×高×4 字节交错 BGRA，复用既有字典和重叠引用规则，不使用 type 5 的通道累加。type 8 解出与 type 6 相同的参考名，两者共用 `0x140092040`，因此复用 `reference_name` / `decode_with_base` 和原有资源上下文边界。仅开放已核对的 32 位输入。

真实 512×512 type 8 及其 type 7 底图的独立 Python 对照、输入/输出哈希和验证边界见游戏档案；合成回归覆盖交错通道、重叠引用、位深/坏偏移/长度错误与参考图边缘块。
