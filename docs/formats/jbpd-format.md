# CMV6 JBPD 帧解码

> 本文描述已核对的实现分支，真实样本与历史验证来自[《アマツツミ》](../games/amatsutsumi/README.md)。其他游戏或引擎版本需单独验证；下文历史停点不代表最新完成度。

证据绑定 `cmvs64.exe` SHA-256 `dc74d2001387ae1aefbdc4204216de5ebb9d3896009280720c4e7a91b42d84f5`。
Rust 核心使用安全、有界的整数运算，不依赖原版 DLL、Windows API 或新增 C++ 核心。

## 原版路径

- `0x1400379f0` 根据 CMV6 签名选择解码模式 2，打开后立即解码帧 0。
- `0x140037900` 获取指定资源；仅当目标帧恰好接在上次解码帧后才允许复用。
- `0x140037620` 锁定 256×256 纹理块，CMV6 / 32 位显示目标调用 `0x1400ab650`。
- `0x1400a0ad0` 读取 JBP 头；`0x1400a0960` 建立频率树；`0x1400b51c0` 为 SSE 整数 IDCT；`0x1400a2300` 为 4:2:0 色彩转换。

JBPD 与 JBP1 共享频率树、系数扫描和分离的 DC/AC 流，但 JBPD 有纹理块布局及可选复用掩码，不能直接将 JBP1 解码器用于影片。
Rust 总是使用原版“不连续帧”路径：所有 MCU 都解码，忽略复用掩码对呈现的优化。
掩码不表示缺失系数，故不需要从首帧累积重放，计时跳帧也可独立解码目标帧。

## 已支持布局

仅接受本作已验证的 `JBPD`、flags `0x58c00002`（可另置 bit 12）、24 位、宽高均为 16 的倍数。
其他模式显式报错，不推广到 JBP1、PB3 type 3 或所有 CMVS 版本。

| 偏移 | 内容 |
|---|---|
| 0 | `JBPD` |
| 4 | 表偏移字段；CMV6 使用字段值 + 4，真实样本 44 + 4 = 48 |
| 8 | flags，bit 27 为显式量化表，bit 12 为复用掩码 |
| 16 / 18 | u16 宽 / 高 |
| 20 | 位深 24 |
| 28 / 32 | DC / AC 字节流长度 |

表区依次为 16×u32 DC 频率、16×u32 AC 频率、16 字节零游程表、64 字节亮度及 64 字节色度量化表。
其后为块行数 u8、块列数 u8、块总数 u16，随后每块以两个 u8 保存 MCU 行数与列数。
布局区相对自身补齐至四字节，存在掩码时再跨过 `ceil(MCU数/8)` 补齐至四字节的掩码。
接着是两个字节流；位按字节低位先取，但系数幅值由所取位依次左移构造。
频率树包括零频率叶子，等频率按节点序号选取。DC 差分在整个帧中累积，保留 i16 回绕；AC 15 结束，AC 0 读取一元游程选择器。

每个 MCU 含四个 8×8 Y 块、一个 Cb 块和一个 Cr 块，按纹理块、块内行、块内列排列。
量化使用自然序表；系数扫描使用 zigzag，乘积按 i16 回绕。
IDCT 逐项保留原 SSE 的 i32 回绕、i16 饱和、算术右移及舍入偏置，不使用浮点近似。
色彩转换将 IDCT 亮度加 128，色度以 2×2 最近邻扩展，固定点系数为 91888、22544、46784、116112，再截断至 0..255。
结果为顶向下、不透明 RGBA；1280×720 最后纹理行只含 13 行 MCU。

所有输入/输出受 64 MiB 研究上限约束；表、布局、流范围、频率溢出、游程、尺寸与容器声明不符均报错。
`CmvIndex::decode_frame` 每次只读取目标帧，不把整部影片载入内存。

## 工具与验证

```powershell
cargo run --offline --release --bin cmvs-cmv -- "E:/Download/AMATSUTSUMI/data/video/op.cmv" --frame 1000 <新文件.png>
cargo run --offline --release --bin cmvs-cmv -- "E:/Download/AMATSUTSUMI/data/video/op.cmv" --check-frames
```

`.rgba` 扩展名导出原始 RGBA，其余输出为 PNG；拒绝覆盖已有文件。
`--check-frames` 解码全部帧并丢弃输出，失败时报告帧号。

独立 Python 实现从只读原版二进制取常数，并以 NumPy 模拟 IDCT 的 SSE 运算；其位流解析、树构建、MCU 拼接与 Rust 独立实现。
op.cmv 的 0、1、100、1000、2906 帧，op2.cmv 的 100、1500、3190 帧，c1.cmv 的 0、200、402 帧，共 11 帧的完整 RGBA 逐字节相同。
op.cmv 第 1000 帧 RGBA SHA-256 为 `ece6dcbe6d8365ef6356a69b83e8a76c9b437a191c248d15c9dba357cb289da0`。
release 全帧检查分别通过 2907、3191、403 帧，共 6501 帧；这不是每帧都做了 Python 对照。
合成测试覆盖亮度分块、色度、AC、游程、掩码独立解码、截断与容器不符；真实素材和研究输出不受 Git 跟踪。

## 宿主集成与限制

`MovieSource::frame` 提供帧来源；桌面启用 `MovieHost::set_decode_frames`，打开时先解出帧 0，再提交音轨请求与 VM 结果。
`advance_decoded` 在目标帧变化时读取并解码，失败保留旧帧和时间，不重复解码同一帧；停止与自然结束清除图像。
`Startup::render_frame` 在全屏影片活动时返回该帧，否则呈现场景；窗口与退出时 `--save-frame` 共用这一输出。
trace 保留显式计时研究路径，不执行 JBPD 解码；因此原有逐指令时间线不变。

影片音轨仍只记录，使用显式帧时钟替代音轨位置；没有音画同步和真实输入跳过。
软件渲染及独立帧检查不证明原版 D3D9 的最终显示逐像素一致；目前未实现影片槽创建 0x2308/0x230e。

2026-10-27：位流读取、频率树与 zigzag 表改为 crate 内共享，供 PB3 type 3 的 JBP1 解码器使用（见 pb3-format.md），JBPD 算法与布局不变，仅错误消息由 JBPD 改为 JBP；op.cmv 第 1000 帧 SHA-256 复核不变。


## CMV9 复用（2026-10-28）

`jbpd::decode` 的 CMV6 入口与布局限制不变；新增内部 masked 入口供 CMV9 使用，复用频率树、量化、IDCT 和颜色转换，加入静态/动态 MCU 位图、名义宽高的边缘裁切及带长度的复用掩码。底图和帧的表偏移有四字节差异，不套用同一偏移。CMV9 的容器、对照结果和支持范围见 [CMV9](cmv9-format.md)。原 CMV6 OP 第 0、1000 帧已与此前独立 Python 输出回归对照一致。
