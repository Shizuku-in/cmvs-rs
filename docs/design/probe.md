# 通用游戏探针设计草案

> 状态：**草案，未实现**。起草基线 `a96c1a1`（2026-11-01）。实施前逐节确认，第 12 节列出待定问题。

## 1. 要解决的问题

目前的运行验证都靠一次性探针完成，它们是为某一款游戏、某一个问题临时写的：

- 忽略目录 `local/` 下约有 200 个 `*_probe.rs` / `*_replay.rs`。很多检查有键盘版和鼠标版两份（如 `mask_probe` / `mask_keyboard_probe`），驱动循环、输入模拟和打印格式各写一遍。
- 探针里写死了游戏路径、系统字体，以及某个脚本内的地址。例如路线重放用"`menu.ps3` 且 PC 为某个固定值"来判断"到达主菜单"，换一款游戏或换一个版本就失效。
- 选项识别、何时点击、何时截图等判断规则散落在各个探针里，没有一处说明它们为什么成立、对哪些构建成立。
- 路线覆盖表和回归记录是先手工运行、再手抄进游戏档案的。19 款作品中只有一款做过整轮路线覆盖。
- 输出只说明"没有报错"。"存读档后状态一致""进出页面后场景复原"这类判定没有统一定义。

档案层（[引擎档案层设计](engine-profiles.md)）已经回答了"这个构建能不能运行"。探针要回答的是下一个问题："能运行到什么程度，哪里不对"，而且要能**用同一套代码**对所有已识别的 CMVS 构建批量回答。

## 2. 目标与非目标

**目标**

1. **与游戏无关。** 探针代码中不出现任何游戏身份、脚本名、脚本地址或系统 ID 常量；对档案层能识别的任意构建，**不提供清单也能运行**。
2. 一个程序覆盖静态检查、剧本路线、输入、页面跳转、存读档、设置、确定性与长时间运行等检查族（第 6 节）。
3. 每个检查结果都注明判定等级（第 7 节），不把"没崩溃"写成"正确"。
4. 可复现：固定随机种子、固定虚拟帧时间、独立用户目录；报告记录全部输入的哈希和参数。
5. 报告可供机器读取，覆盖表和跨游戏汇总表由报告生成，不再手抄。

**非目标**

- 不替代单元测试。格式和语义的正确性仍由 `tests/` 中的合成数据测试负责；探针只做整机运行层面的检查。
- 不绕过命令闸门。探针遵守 M3 策略，碰到闸门停止就记为一条发现（`blocked`），不加放行参数掩盖。研究时允许显式传 `--allow-presumed` / `--allow-unreviewed`，但报告会标明。
- 不判定"与原版一致"，除非有原版参考数据（L2）。
- 不驱动桌面窗口。探针只在无头运行时层工作，窗口、缩放和全屏另行处理。
- 仓库不保存游戏数据或探针输出，只保存代码、合成测试，以及经过审阅的清单和摘要。

## 3. 通用性约束

本节是设计的核心。后面所有章节都必须满足这五条规则；违反任何一条，都说明有游戏知识混进了代码。

### 规则 1：代码中不出现游戏身份

探针 crate 中禁止出现以下内容：游戏目录名、exe 哈希、脚本文件名字面量（如 `b"menu.ps3"`）、脚本内 PC 常量、系统变量编号、按钮组槽位常量。这条由测试检查：扫描探针源码，遇到 `.ps2`/`.ps3` 字节串字面量即失败（测试夹具目录除外）。

引擎层常量（命令号、宿主结构、文件格式）可以出现，前提是它们已在档案层或分派层登记。它们属于"引擎"，不属于"某款游戏"。

### 规则 2：身份只来自档案层

会话开始时，调用与 `cmvs-profile identify` 相同的识别逻辑，得到档案 ID、各文件哈希和档案状态。未登记的构建只运行静态族（S）的子集，报告为 `unsupported-profile`，不猜测。

### 规则 3：状态只从引擎层观察判断

"现在处于什么状态"只能由第 5 节的观察量推出：消息等待、按钮组、当前脚本切换、待处理系统命令、各宿主状态，以及各类摘要值。脚本名可以出现在报告里供人阅读，但不能作为判断条件。

### 规则 4：差异按"能力"处理，不按"游戏"分支

不同构建之间的差异（CPZ 版本、`.ps2`/`.ps3`、是否有 x64、是否有 `key.cfg`、快照能否构建、某个宿主命令是否已放行）统一表示为会话的**能力集合**。每个检查声明自己需要哪些能力；缺少时结果记为 `skipped(缺少的能力)`，不记为失败，也不写 `if 某游戏`。

### 规则 5：清单只做纠正，只用引擎层词汇

自动识别可能猜错，例如把一个普通按钮组当成选项，或分不清哪个页面是设置页。这时用每款游戏一份的可选清单纠正。清单的约束：

- 只能是数据：按钮组槽位、按钮 ID、脚本名、系统 ID、页面签名（第 5.3 节），以及给人看的标签。不能写判断逻辑或输入序列。
- 每一条都要写明证据，即依据哪份报告的哪个观察。
- 报告列出本次用到了哪些清单条目，以及自动识别与清单不一致的地方。不一致本身是一条发现：说明自动识别规则需要改进，而不是给清单再加一条。
- 清单与档案 ID 绑定。同一款游戏的不同构建，各自用自己的清单或明确声明继承。

清单的目标是越写越少。一条纠正规则如果在两款以上的游戏中都成立，就应改成通用规则放进观察层，再删掉对应的清单条目。

## 4. 架构

```text
          ┌──────────── 报告层：JSONL 事件 + 摘要 + 可选截图 ────────────┐
          │                                                             │
 检查族 ──┤ S 静态  R 路线  I 输入  P 页面  V 存读档  C 设置  D 确定性  L 长时间 │
          │                         │                                   │
          │                判定器（L0 / L1 / L2）                       │
          │                         │                                   │
          │   观察层：Observation → 事件流（选项、页面、等待、卡死 …）    │
          │                         │                                   │
          └ 会话层：档案识别 + 能力集合 + Startup + 输入设备 + 虚拟时间 + 隔离用户目录 ┘
```

新建 `crates/cmvs-probe`（库 + `cmvs-probe` 程序），只依赖 `cmvs-core`，另外按需依赖 `cmvs-desktop` 的字体模块。字体由参数传入；没有字体时，依赖文字排版的检查记为 `skipped(font)`。

### 4.1 会话层

- **输入**：游戏根目录（只读）、可选的清单路径、输出目录。三者都是参数；代码没有默认游戏路径。
- **隔离**：每个会话在输出目录下新建用户数据目录，从不写入游戏目录。需要"已有存档"的检查，先把指定存档**复制**进去。
- **确定性**：固定 `--rand-seed`、虚拟帧时间（默认 16 ms，可配置）、录制型平台和音频后端。
- **能力集合**：由档案层识别结果和文件探测生成，例如 `script.ps3`、`cpz6`、`key-config`、`snapshot-capture`、`font`、`gate:<命令号>`。
- **会话复位**：从某个起点重新开始，起点可以是初始状态、存档或会话快照（见 5.4）。路线探索和破坏性页面动作都依赖复位。

### 4.2 统一动作与输入设备

检查只发出抽象动作，由输入设备翻译成具体输入：

| 动作 | 鼠标设备 | 键盘设备 |
|---|---|---|
| `Advance` | 左键点击 | `key.cfg` 中的确定键 |
| `SkipHold(n)` | — | 按住跳过键 n 帧 |
| `Backlog` / `Forward` | 滚轮上 / 下 | `key.cfg` 对应键 |
| `Menu` / `Cancel` | 右键 | `key.cfg` 对应键 |
| `Press(group, button)` | 移动到按钮中心并点击 | 方向键导航到该按钮后确认 |
| `Wheel(±n)`、`Key(code)` | 原样 | 原样 |

键盘设备读取游戏自带的 `key.cfg`（复用 `KeyBindings::parse`）；没有 `key.cfg` 时缺少 `key-config` 能力，键盘相关检查跳过。同一个检查用 `--device mouse|keyboard|both` 参数运行，不再写成两个探针。`Press` 走键盘时使用按钮的 `links` 导航，导航不到目标本身就是一条发现。

## 5. 观察层

### 5.1 每次让出时的观察量

每次 VM 让出（`Yield`）时采集一份 `Observation`，全部来自 `Startup` 的公开访问器：

| 观察量 | 来源 |
|---|---|
| 当前脚本、PC、步数、待处理系统命令、重复计数 | `machine()`、`steps()` |
| 消息等待、消息标志、已读状态 | `messages()`、`message_flags()` |
| 按钮组：槽位、按钮数量、启用状态、矩形、当前按钮 | `buttons()` |
| 回想条数与最后一条 | `history()` |
| 存档菜单状态、确认弹窗 | `save_menu()` |
| 设置值（文字速度、自动推进、跳过已读等） | `settings()` |
| 音频通道与正在播放的资源 | `audio()` |
| 影片、场景对象数、序列和计时器数量 | `movies()`、`scene()`、`sequence()`、`timers()` |
| 事件：`Quit`、`Unhandled`、快照事件、闸门错误 | `tick()` 的返回值和错误 |

观察层不需要的字段，只有在某个检查用到时才加入访问器。不为探针新增"游戏专用"接口。

### 5.2 摘要值

判定靠比较摘要值，而不是比较截图：

- **VM 摘要**：当前脚本、PC、调用栈、局部变量、全局变量区。
- **画面摘要**：场景树、消息窗口、文字、按钮组的可见状态。必要时再加渲染帧的哈希。
- **持久摘要**：系统存档（`system.dat`）的字节，以及解码后按区段的摘要。

计时器、随机数状态、帧计数等易变字段要从摘要中排除。排除哪些字段属于引擎层定义，与[快照格式](../formats/snapshot-format.md)一起按版本维护，不按游戏维护。摘要不一致时，报告给出第一个不同的区段，便于定位。

### 5.3 派生事件与页面签名

观察层把连续的观察量转换成事件：

- `ScriptEntered`、`WaitForAdvance`、`ButtonGroupShown/Hidden`、`Quit`、`GateStop`。
- `Stalled`：连续 N 次让出，VM、画面摘要和输入需求都不变。默认 N 取几秒的虚拟时间，可通过参数调整。
- **页面签名** = 可见按钮组集合（槽位、按钮数、按矩形量化后的哈希）+ 当前脚本。页面的定义只依赖这个签名，**不需要知道"这是设置页"**。名称只是给人看的标签：先用脚本名、按钮图像资源名推测，再由清单纠正。这是页面遍历能做到与游戏无关的关键。
- `ChoicePresented`：剧情进行中出现一个新的按钮组，并且该组按钮数与最近放置的文字条数一致。这条规则来自现有路线重放，需要在多款游戏上验证。有多个候选组时，输出 `ambiguous-choice` 和所有候选，由清单指定槽位，不靠猜。
- `TitleReached`：会话第一次稳定在某个页面签名上时，把它记为"起始页面"；之后再回到这个签名就产生该事件。不靠脚本名判断。

### 5.4 会话快照与分叉

路线探索和破坏性动作都需要"回到某个状态再走另一条路"。实现方式分三档，都在会话层实现，检查代码不感知用的是哪一档：

1. **重放**：从起点重新执行，按已记录的动作序列走到分叉点。不依赖其他能力，但慢。
2. **存读档分叉**：在分叉点用引擎自己的存档功能写入隔离用户目录，再读档。前提是 V 族的往返检查在该构建上达到 L1。
3. **内存快照**：给运行状态加整体复制或序列化。目前 `Startup` 不能复制，工作量最大，需要单独设计。

会话默认用重放。V 族往返检查通过后，自动升级到存读档分叉，报告注明实际用了哪一档。

## 6. 检查清单

检查 ID 使用"族字母 + 序号"，在所有游戏中保持不变，跨游戏汇总时以检查 ID 为列。

| ID | 检查 | 需要的能力 | 最高等级 |
|---|---|---|---|
| **S 静态** | | | |
| S1 | 档案识别、文件哈希、能力集合 | — | L0 |
| S2 | 全部脚本可以解析、反汇编、解析跳转目标 | 脚本格式 | L0 |
| S3 | 静态可达的系统命令按闸门状态分类，列出可达但为 Absent/Unreviewed/Presumed 的命令 | 档案 | L0 |
| S4 | 脚本中引用的图像、语音、BGM、影片资源都存在且能解码头部 | 封包格式 | L0 |
| S5 | 自带的系统存档、存档能被检查工具解析 | 存档格式 | L0 |
| **R 剧本路线** | | | |

| I4 | 回想：滚动、语音重播、退出回想后状态复原 | — | L1 |
| I5 | 随机输入测试：固定种子随机发出动作，持续检查不变量 | — | L0 |

| V5 | 系统存档跨进程保持：已读、解锁、设置 | — | L1 |
| **C 设置** | | | |
| C1 | 遍历设置页中的每个控件，设置值发生预期变化 | P1 | L0 |
| C2 | 设置写入系统存档，重启后保持 | V5 | L1 |
| C3 | 设置在运行时生效：文字速度改变等待时长，音量改变混音参数，跳过已读改变 R5 的行为 | — | L1 |
| C4 | 恢复默认值后，与首次运行的设置一致 | — | L1 |
| **D 确定性与容错** | | | |
| D1 | 同样的输入跑两遍，事件流和摘要逐项一致 | — | L1 |

D1 是所有 L1 比较的前提。D1 不通过时，其他 L1 结果一律降级为 `inconclusive`。

## 7. 判定等级与结果状态

| 等级 | 含义 | 数据来源 |
|---|---|---|
| L0 冒烟 | 不报错、不碰闸门、不卡死 | 本次运行 |
| L1 自洽 | 往返或不变量成立（存读档、页面进出、确定性、跨设备） | 本次运行内的比较 |
| L2 对照原版 | 与原版 exe 采集的参考数据一致（截图、系统存档、存档） | 外部参考包 |

结果状态：`pass`、`fail`、`skipped(原因)`、`blocked(命令号, PC)`、`inconclusive(原因)`。表格中的"最高等级"是这个检查最多能证明到哪一级；报告记录的是**实际达到**的等级。L2 需要先定义参考包的采集方法，见第 12 节。

## 8. 报告

每个会话的输出目录包含：

- `events.jsonl`：事件流，每行带步数、脚本:PC、事件类型和负载。
- `summary.json`：探针版本与提交号、档案 ID、文件哈希、清单哈希及用到的条目、参数、能力集合，以及每个检查的结果和等级。
- `coverage.tsv`：R3 的逐脚本覆盖表，取代手抄表格。
- `frames/`：可选，在失败点或指定事件时截图。

另有一个汇总命令，读取多个 `summary.json`，生成"游戏 × 检查 ID"矩阵。按归档规则，生成的摘要放进 `docs/games/<游戏标识>/`，原始输出留在 `local/` 或仓库外。

## 9. 关键算法

### 9.1 选项树探索（R2、R4）

1. 从起始页面进入新游戏，按 `Advance` 推进；开启跳过时用 `SkipHold`。
2. 遇到 `ChoicePresented` 时，记录状态键（脚本、PC、全局变量区摘要），然后把每个启用的按钮加入待探索栈。状态键见过的分支合并，避免重复探索。
3. 用当前档位的分叉方式（5.4）进入每个分支，直到出现 `TitleReached`、`Quit`、`blocked` 或单分支步数预算耗尽。
4. 结局的定义是：回到起始页面时，持久摘要发生了变化。这条定义不依赖结局脚本名或片尾演出。
5. R4 以上一轮结束时的系统存档作为下一轮的起点重跑；某一轮没有新结局、新选项时停止。

报告按选择路径列出各分支。如果有清单标签，就附上选项文字的可读形式。

### 9.2 页面图遍历（P1–P3）

1. 节点是页面签名，边是"在页面 A 执行动作 x 后到达页面 B"。
2. 在每个节点上依次尝试：每个启用按钮的 `Press`，以及 `Cancel`、`Menu`。每次尝试前都把会话复位到该节点，保证各次尝试互相独立。
3. 能回到父节点的动作记为该节点的"返回边"。P2 沿返回边比较摘要。
4. 引起 `Quit` 或回到起始页面的边标记为破坏性边（P3）。这类边只验证事件本身，不继续向下展开。
5. 剧情中的入口：在 R2 路线上抽样若干消息等待点，每个点发出 `Menu` 后各遍历一次。

存档页和设置页在这里只当作普通节点遍历。它们的语义检查分别由 V 族和 C 族负责，靠页面签名加清单标签找到对应页面。

## 10. 与现有工具和流程的关系

- `cmvs-trace` 保持为单条执行路径的研究工具；探针复用同一个分派入口和闸门，不另建执行链。
- `cmvs-profile identify` 的识别逻辑提取成库函数，供探针调用。
- `local/` 中的一次性探针按第 6 节的检查 ID 归类迁移：路线重放 → R2，鉴赏模式重放 → P1/P4，键盘与鼠标两版 → 一个 I 族检查加设备参数，快照和存档类探针 → V 族。迁移完成的探针不再新增；新问题优先写成检查，或写成某个检查的参数。
- 新游戏接入（[研究约定](../research.md)）增加一步：登记档案后，用无清单模式运行一次，结果附在游戏档案中，作为初始状态。

## 11. 分阶段计划

每个阶段的验收都要求**至少两款游戏**，防止设计只适配一款游戏。当前可用的组合是《アマツツミ》和《クロノクロック》，后者允许停在闸门上（`blocked`）。

| 阶段 | 内容 | 验收 |
|---|---|---|
| P1 | 会话层、统一输入设备、观察层、报告层；S1–S3、R1、D1；源码中无游戏常量的测试 | 两款游戏无清单运行，产出 `summary.json`；《アマツツミ》D1 通过 |
| P2 | `ChoicePresented`、重放式 R2、R3 | 《アマツツミ》无清单复现现有 5 条路线及 OP 的覆盖数字；《クロノクロック》走到第一个闸门停止点或第一个选项 |
| P3 | V1–V5、存读档分叉；D2、D3 | 《アマツツミ》V1/V2 达到 L1，R2 改用存读档分叉后结果与重放一致 |
| P4 | 页面图 P1–P4、C1–C4、I1–I5、L1 | 页面图在两款游戏上无清单生成；清单条目数作为通用性指标一并报告 |
| P5 | 全部 19 款作品批量运行与汇总矩阵；R4、R5 | 矩阵生成，所有未通过项都对应到检查 ID 和闸门命令号 |
| P6 | L2 参考包与对照 | 另行设计 |

## 12. 待确认问题

1. **分叉档位。** 先用重放（5.4 第 1 档），P3 之后升级到存读档分叉。是否需要尽早投入内存快照？
2. **清单存放位置。** 建议放在 `docs/games/<游戏标识>/probe.toml`。清单只含引擎层词汇和证据引用，不含游戏数据，符合归档规则。
3. **选项识别规则。** 第 5.3 节的规则只在一款游戏上观察过。P2 前需要在《クロノクロック》上验证，否则先只在清单中声明候选按钮组。
4. **摘要的排除字段。** 哪些字段属于"易变"，要和快照格式一起确定。这决定了 L1 检查是否可信。
5. **L2 参考包。** 原版的参考数据怎么采集（截图时机、存档导出），以及采集结果放在哪里。
6. **预算默认值。** 单分支步数、总时长、`Stalled` 的阈值。全系列批量运行需要一组合适的默认值。
