# 通用游戏探针设计草案

> 状态：**已实现**（2026-11-01，见第 13–16 节）。第 6 节的全部检查均已实现；L2 原版对照需要另行设计参考数据的采集。起草基线 `a96c1a1`。实施前逐节确认，第 12 节列出待定问题。

## 1. 要解决的问题

目前的运行验证都靠一次性探针完成，它们是为某一款游戏、某一个问题临时写的：

- 忽略目录 `local/` 下约有 200 个 `*_probe.rs` / `*_replay.rs`。很多检查有键盘版和鼠标版两份（如 `mask_probe` / `mask_keyboard_probe`），驱动循环、输入模拟和打印格式各写一遍。
- 探针里写死了游戏路径、系统字体，以及某个脚本内的地址。例如路线重放用"`menu.ps3` 且 PC 为某个固定值"来判断"到达主菜单"，换一款游戏或换一个版本就失效。
- 选项识别、何时点击、何时截图等判断规则散落在各个探针里，没有一处说明它们为什么成立、对哪些构建成立。
- 路线覆盖表和回归记录是先手工运行、再手抄进游戏档案的。19 款作品中只有一款做过整轮路线覆盖。
- 输出只说明"没有报错"。"存读档后状态一致""进出页面后场景复原"这类判定没有统一定义。

档案层（[引擎档案层设计](engine-profiles.md)）已经回答了"这个构建能不能运行"。探针要回答的是下一个问题："能运行到什么程度，哪里不对"，而且要能**用同一套代码**对所有已识别的 CMVS 构建批量回答。

## 2. 目标与非目标

**目标**

1. **与游戏无关。** 探针代码中不出现任何游戏身份、脚本名、脚本地址或系统 ID 常量；对档案层能识别的任意构建，**不提供清单也能运行**。
2. 一个程序覆盖静态检查、剧本路线、输入、页面跳转、存读档、设置、确定性与长时间运行等检查族（第 6 节）。
3. 每个检查结果都注明判定等级（第 7 节），不把"没崩溃"写成"正确"。
4. 可复现：固定随机种子、固定虚拟帧时间、独立用户目录；报告记录全部输入的哈希和参数。
5. 报告可供机器读取，覆盖表和跨游戏汇总表由报告生成，不再手抄。

**非目标**

- 不替代单元测试。格式和语义的正确性仍由 `tests/` 中的合成数据测试负责；探针只做整机运行层面的检查。
- 不绕过命令闸门。探针遵守 M3 策略，碰到闸门停止就记为一条发现（`blocked`），不加放行参数掩盖。研究时允许显式传 `--allow-presumed` / `--allow-unreviewed`，但报告会标明。
- 不判定"与原版一致"，除非有原版参考数据（L2）。
- 不驱动桌面窗口。探针只在无头运行时层工作，窗口、缩放和全屏另行处理。
- 仓库不保存游戏数据或探针输出，只保存代码、合成测试，以及经过审阅的清单和摘要。

## 3. 通用性约束

本节是设计的核心。后面所有章节都必须满足这五条规则；违反任何一条，都说明有游戏知识混进了代码。

### 规则 1：代码中不出现游戏身份

探针 crate 中禁止出现以下内容：游戏目录名、exe 哈希、脚本文件名字面量（如 `b"menu.ps3"`）、脚本内 PC 常量、系统变量编号、按钮组槽位常量。这条由测试检查：扫描探针源码，遇到 `.ps2`/`.ps3` 字节串字面量即失败（测试夹具目录除外）。

引擎层常量（命令号、宿主结构、文件格式）可以出现，前提是它们已在档案层或分派层登记。它们属于"引擎"，不属于"某款游戏"。

### 规则 2：身份只来自档案层

会话开始时，调用与 `cmvs-profile identify` 相同的识别逻辑，得到档案 ID、各文件哈希和档案状态。未登记的构建只运行静态族（S）的子集，报告为 `unsupported-profile`，不猜测。

### 规则 3：状态只从引擎层观察判断

"现在处于什么状态"只能由第 5 节的观察量推出：消息等待、按钮组、当前脚本切换、待处理系统命令、各宿主状态，以及各类摘要值。脚本名可以出现在报告里供人阅读，但不能作为判断条件。

### 规则 4：差异按"能力"处理，不按"游戏"分支

不同构建之间的差异（CPZ 版本、`.ps2`/`.ps3`、是否有 x64、是否有 `key.cfg`、快照能否构建、某个宿主命令是否已放行）统一表示为会话的**能力集合**。每个检查声明自己需要哪些能力；缺少时结果记为 `skipped(缺少的能力)`，不记为失败，也不写 `if 某游戏`。

### 规则 5：清单只做纠正，只用引擎层词汇

自动识别可能猜错，例如把一个普通按钮组当成选项，或分不清哪个页面是设置页。这时用每款游戏一份的可选清单纠正。清单的约束：

- 只能是数据：按钮组槽位、按钮 ID、脚本名、系统 ID、页面签名（第 5.3 节），以及给人看的标签。不能写判断逻辑或输入序列。
- 每一条都要写明证据，即依据哪份报告的哪个观察。
- 报告列出本次用到了哪些清单条目，以及自动识别与清单不一致的地方。不一致本身是一条发现：说明自动识别规则需要改进，而不是给清单再加一条。
- 清单与档案 ID 绑定。同一款游戏的不同构建，各自用自己的清单或明确声明继承。

清单的目标是越写越少。一条纠正规则如果在两款以上的游戏中都成立，就应改成通用规则放进观察层，再删掉对应的清单条目。

## 4. 架构

```text
          ┌──────────── 报告层：JSONL 事件 + 摘要 + 可选截图 ────────────┐
          │                                                             │
 检查族 ──┤ S 静态  R 路线  I 输入  P 页面  V 存读档  C 设置  D 确定性  L 长时间 │
          │                         │                                   │
          │                判定器（L0 / L1 / L2）                       │
          │                         │                                   │
          │   观察层：Observation → 事件流（选项、页面、等待、卡死 …）    │
          │                         │                                   │
          └ 会话层：档案识别 + 能力集合 + Startup + 输入设备 + 虚拟时间 + 隔离用户目录 ┘
```

新建 `crates/cmvs-probe`（库 + `cmvs-probe` 程序），只依赖 `cmvs-core`，另外按需依赖 `cmvs-desktop` 的字体模块。字体由参数传入；没有字体时，依赖文字排版的检查记为 `skipped(font)`。

### 4.1 会话层

- **输入**：游戏根目录（只读）、可选的清单路径、输出目录。三者都是参数；代码没有默认游戏路径。
- **隔离**：每个会话在输出目录下新建用户数据目录，从不写入游戏目录。需要"已有存档"的检查，先把指定存档**复制**进去。
- **确定性**：固定 `--rand-seed`、虚拟帧时间（默认 16 ms，可配置）、录制型平台和音频后端。
- **能力集合**：由档案层识别结果和文件探测生成，例如 `script.ps3`、`cpz6`、`key-config`、`snapshot-capture`、`font`、`gate:<命令号>`。
- **会话复位**：从某个起点重新开始，起点可以是初始状态、存档或会话快照（见 5.4）。路线探索和破坏性页面动作都依赖复位。

### 4.2 统一动作与输入设备

检查只发出抽象动作，由输入设备翻译成具体输入：

| 动作 | 鼠标设备 | 键盘设备 |
|---|---|---|
| `Advance` | 左键点击 | `key.cfg` 中的确定键 |
| `SkipHold(n)` | — | 按住跳过键 n 帧 |
| `Backlog` / `Forward` | 滚轮上 / 下 | `key.cfg` 对应键 |
| `Menu` / `Cancel` | 右键 | `key.cfg` 对应键 |
| `Press(group, button)` | 移动到按钮中心并点击 | 方向键导航到该按钮后确认 |
| `Wheel(±n)`、`Key(code)` | 原样 | 原样 |

键盘设备读取游戏自带的 `key.cfg`（复用 `KeyBindings::parse`）；没有 `key.cfg` 时缺少 `key-config` 能力，键盘相关检查跳过。同一个检查用 `--device mouse|keyboard|both` 参数运行，不再写成两个探针。`Press` 走键盘时使用按钮的 `links` 导航，导航不到目标本身就是一条发现。

## 5. 观察层

### 5.1 每次让出时的观察量

每次 VM 让出（`Yield`）时采集一份 `Observation`，全部来自 `Startup` 的公开访问器：

| 观察量 | 来源 |
|---|---|
| 当前脚本、PC、步数、待处理系统命令、重复计数 | `machine()`、`steps()` |
| 消息等待、消息标志、已读状态 | `messages()`、`message_flags()` |
| 按钮组：槽位、按钮数量、启用状态、矩形、当前按钮 | `buttons()` |
| 回想条数与最后一条 | `history()` |
| 存档菜单状态、确认弹窗 | `save_menu()` |
| 设置值（文字速度、自动推进、跳过已读等） | `settings()` |
| 音频通道与正在播放的资源 | `audio()` |
| 影片、场景对象数、序列和计时器数量 | `movies()`、`scene()`、`sequence()`、`timers()` |
| 事件：`Quit`、`Unhandled`、快照事件、闸门错误 | `tick()` 的返回值和错误 |

观察层不需要的字段，只有在某个检查用到时才加入访问器。不为探针新增"游戏专用"接口。

### 5.2 摘要值

判定靠比较摘要值，而不是比较截图：

- **VM 摘要**：当前脚本、PC、调用栈、局部变量、全局变量区。
- **画面摘要**：场景树、消息窗口、文字、按钮组的可见状态。必要时再加渲染帧的哈希。
- **持久摘要**：系统存档（`system.dat`）的字节，以及解码后按区段的摘要。

计时器、随机数状态、帧计数等易变字段要从摘要中排除。排除哪些字段属于引擎层定义，与[快照格式](../formats/snapshot-format.md)一起按版本维护，不按游戏维护。摘要不一致时，报告给出第一个不同的区段，便于定位。

### 5.3 派生事件与页面签名

观察层把连续的观察量转换成事件：

- `ScriptEntered`、`WaitForAdvance`、`ButtonGroupShown/Hidden`、`Quit`、`GateStop`。
- `Stalled`：连续 N 次让出，VM、画面摘要和输入需求都不变。默认 N 取几秒的虚拟时间，可通过参数调整。
- **页面签名** = 可见按钮组集合（槽位、按钮数、按矩形量化后的哈希）+ 当前脚本。页面的定义只依赖这个签名，**不需要知道"这是设置页"**。名称只是给人看的标签：先用脚本名、按钮图像资源名推测，再由清单纠正。这是页面遍历能做到与游戏无关的关键。
- `ChoicePresented`：剧情进行中出现一个新的按钮组，并且该组按钮数与最近放置的文字条数一致。这条规则来自现有路线重放，需要在多款游戏上验证。有多个候选组时，输出 `ambiguous-choice` 和所有候选，由清单指定槽位，不靠猜。
- `TitleReached`：会话第一次稳定在某个页面签名上时，把它记为"起始页面"；之后再回到这个签名就产生该事件。不靠脚本名判断。

### 5.4 会话快照与分叉

路线探索和破坏性动作都需要"回到某个状态再走另一条路"。实现方式分三档，都在会话层实现，检查代码不感知用的是哪一档：

1. **重放**：从起点重新执行，按已记录的动作序列走到分叉点。不依赖其他能力，但慢。
2. **存读档分叉**：在分叉点用引擎自己的存档功能写入隔离用户目录，再读档。前提是 V 族的往返检查在该构建上达到 L1。
3. **内存快照**：给运行状态加整体复制或序列化。目前 `Startup` 不能复制，工作量最大，需要单独设计。

会话默认用重放。V 族往返检查通过后，自动升级到存读档分叉，报告注明实际用了哪一档。

## 6. 检查清单

检查 ID 使用"族字母 + 序号"，在所有游戏中保持不变，跨游戏汇总时以检查 ID 为列。

| ID | 检查 | 需要的能力 | 最高等级 |
|---|---|---|---|
| **S 静态** | | | |
| S1 | 档案识别、文件哈希、能力集合 | — | L0 |
| S2 | 全部脚本可以解析、反汇编、解析跳转目标 | 脚本格式 | L0 |
| S3 | 静态可达的系统命令按闸门状态分类，列出可达但为 Absent/Unreviewed/Presumed 的命令 | 档案 | L0 |
| S4 | 脚本中引用的图像、语音、BGM、影片资源都存在且能解码头部 | 封包格式 | L0 |
| S5 | 自带的系统存档、存档能被检查工具解析 | 存档格式 | L0 |
| **R 剧本路线** | | | |
| R1 | 首次启动到达起始页面，确认能进入新游戏 | — | L0 |
| R2 | 选项树探索：每个分支走到结局或预算上限，按选择路径命名（如 `0.1.0`） | `ChoicePresented` 能识别 | L0 |
| R3 | 地址覆盖：已执行地址与静态可达地址的比例，按脚本列出 | S2 | L0 |

| **I 输入** | | | |
| I1 | 消息等待处逐个触发全部抽象动作，不报错、不卡死 | — | L0 |
| I2 | 鼠标与键盘设备走同一段，结束时 VM 摘要相同 | `key-config` | L1 |
| I3 | 跳过、自动推进、隐藏窗口进入后再退出，画面摘要能复原 | — | L1 |
| I4 | 回想：滚动、语音重播、退出回想后状态复原 | — | L1 |
| I5 | 随机输入测试：固定种子随机发出动作，持续检查不变量 | — | L0 |
| **P 页面** | | | |
| P1 | 从起始页面和剧情中的菜单出发，广度优先遍历页面图 | — | L0 |
| P2 | 进入任意页面后再返回，VM 与画面摘要和进入前一致 | P1 | L1 |
| P3 | 破坏性按钮（返回标题、退出、结束游戏）引起预期事件，会话复位后能继续遍历 | 会话复位 | L0 |

| V1 | 剧情中任意点存档后读档，VM 与画面摘要一致 | `snapshot-capture` | L1 |
| V2 | 存档"写入→读取→再写入"，字节一致 | 同上 | L1 |
| V3 | 重启进程后读档、从起始页面读档、快速存读档 | 同上 | L1 |
| V4 | 槽位翻页、覆盖、删除、确认弹窗；槽位标题与时间正确 | 同上 | L1 |
| V5 | 系统存档跨进程保持：已读、解锁、设置 | — | L1 |
| **C 设置** | | | |
| C1 | 遍历设置页中的每个控件，设置值发生预期变化 | P1 | L0 |
| C2 | 设置写入系统存档，重启后保持 | V5 | L1 |
| C3 | 设置在运行时生效：文字速度改变等待时长，音量改变混音参数，跳过已读改变 R5 的行为 | — | L1 |
| C4 | 恢复默认值后，与首次运行的设置一致 | — | L1 |
| **D 确定性与容错** | | | |
| D1 | 同样的输入跑两遍，事件流和摘要逐项一致 | — | L1 |

| **L 长时间运行** | | | |
| L1 | 整条路线过程中，对象、音频通道、按钮组、计时器的数量不持续增长 | R2 | L0 |

D1 是所有 L1 比较的前提。D1 不通过时，其他 L1 结果一律降级为 `inconclusive`。

## 7. 判定等级与结果状态

| 等级 | 含义 | 数据来源 |
|---|---|---|
| L0 冒烟 | 不报错、不碰闸门、不卡死 | 本次运行 |
| L1 自洽 | 往返或不变量成立（存读档、页面进出、确定性、跨设备） | 本次运行内的比较 |
| L2 对照原版 | 与原版 exe 采集的参考数据一致（截图、系统存档、存档） | 外部参考包 |

结果状态：`pass`、`fail`、`skipped(原因)`、`blocked(命令号, PC)`、`inconclusive(原因)`。表格中的"最高等级"是这个检查最多能证明到哪一级；报告记录的是**实际达到**的等级。L2 需要先定义参考包的采集方法，见第 12 节。

## 8. 报告

每个会话的输出目录包含：

- `events.jsonl`：事件流，每行带步数、脚本:PC、事件类型和负载。
- `summary.json`：探针版本与提交号、档案 ID、文件哈希、清单哈希及用到的条目、参数、能力集合，以及每个检查的结果和等级。
- `coverage.tsv`：R3 的逐脚本覆盖表，取代手抄表格。
- `frames/`：可选，在失败点或指定事件时截图。

另有一个汇总命令，读取多个 `summary.json`，生成"游戏 × 检查 ID"矩阵。按归档规则，生成的摘要放进 `docs/games/<游戏标识>/`，原始输出留在 `local/` 或仓库外。

## 9. 关键算法

### 9.1 选项树探索（R2、R4）

1. 从起始页面进入新游戏，按 `Advance` 推进；开启跳过时用 `SkipHold`。
2. 遇到 `ChoicePresented` 时，记录状态键（脚本、PC、全局变量区摘要），然后把每个启用的按钮加入待探索栈。状态键见过的分支合并，避免重复探索。
3. 用当前档位的分叉方式（5.4）进入每个分支，直到出现 `TitleReached`、`Quit`、`blocked` 或单分支步数预算耗尽。
4. 结局的定义是：回到起始页面时，持久摘要发生了变化。这条定义不依赖结局脚本名或片尾演出。
5. R4 以上一轮结束时的系统存档作为下一轮的起点重跑；某一轮没有新结局、新选项时停止。

报告按选择路径列出各分支。如果有清单标签，就附上选项文字的可读形式。

### 9.2 页面图遍历（P1–P3）

1. 节点是页面签名，边是"在页面 A 执行动作 x 后到达页面 B"。
2. 在每个节点上依次尝试：每个启用按钮的 `Press`，以及 `Cancel`、`Menu`。每次尝试前都把会话复位到该节点，保证各次尝试互相独立。
3. 能回到父节点的动作记为该节点的"返回边"。P2 沿返回边比较摘要。
4. 引起 `Quit` 或回到起始页面的边标记为破坏性边（P3）。这类边只验证事件本身，不继续向下展开。
5. 剧情中的入口：在 R2 路线上抽样若干消息等待点，每个点发出 `Menu` 后各遍历一次。

存档页和设置页在这里只当作普通节点遍历。它们的语义检查分别由 V 族和 C 族负责，靠页面签名加清单标签找到对应页面。

## 10. 与现有工具和流程的关系

- `cmvs-trace` 保持为单条执行路径的研究工具；探针复用同一个分派入口和闸门，不另建执行链。
- `cmvs-profile identify` 的识别逻辑提取成库函数，供探针调用。
- `local/` 中的一次性探针按第 6 节的检查 ID 归类迁移：路线重放 → R2，鉴赏模式重放 → P1/P4，键盘与鼠标两版 → 一个 I 族检查加设备参数，快照和存档类探针 → V 族。迁移完成的探针不再新增；新问题优先写成检查，或写成某个检查的参数。
- 新游戏接入（[研究约定](../research.md)）增加一步：登记档案后，用无清单模式运行一次，结果附在游戏档案中，作为初始状态。

## 12. 待确认问题

1. **分叉档位。** 先用重放（5.4 第 1 档），P3 之后升级到存读档分叉。是否需要尽早投入内存快照？
2. **清单存放位置。** 建议放在 `docs/games/<游戏标识>/probe.toml`。清单只含引擎层词汇和证据引用，不含游戏数据，符合归档规则。
3. **选项识别规则。** 第 5.3 节的规则只在一款游戏上观察过。P2 前需要在《クロノクロック》上验证，否则先只在清单中声明候选按钮组。
4. **摘要的排除字段。** 哪些字段属于"易变"，要和快照格式一起确定。这决定了 L1 检查是否可信。
5. **L2 参考包。** 原版的参考数据怎么采集（截图时机、存档导出），以及采集结果放在哪里。
6. **预算默认值。** 单分支步数、总时长、`Stalled` 的阈值。全系列批量运行需要一组合适的默认值。

## 14. P2 进展（2026-11-01）

实现 R2（重放式选项树探索）和 R3（地址覆盖）。两者运行时间长，只在 `--checks` 中列出时运行；新增 `--max-routes`（默认 16）和 `--no-route-skip`。

实施中确定的规则：

- **进入剧情**：在起始页面上按顺序逐个按下启用按钮，每个按钮都从新会话开始；第一个之后出现消息等待的按钮就是剧情入口。其余按钮的结果（打开页面、无变化、退出、被闸门阻止）记入报告。没有按钮能进入剧情、且有按钮被闸门阻止时，R2 记为 `blocked`。
- **选项**：消息等待期间出现过的按钮组记为常驻组。剧情中，不在消息等待、没有渐变时，一个非常驻且有启用按钮的组连续 30 帧不变，即视为选项。同时出现多个这样的组时，报告 `ambiguous-choice` 并停止该路线。已回答过的选项形状，在没有任何候选组之后才会再次参与判断，因此后面出现的同形状选项不会被漏掉。
- **路线结束**：剧情结束后回到起始页面所在的脚本、并且页面稳定时，路线结束。不要求页面与起始页面完全相同：《アマツツミ》通关后标题从 4 个按钮变为 5 个。路线停留在起始页面的脚本中时不做选项判断，否则标题按钮会先被当作选项（30 帧早于页面稳定所需的 60 帧）。
- **合并**：选项处的状态键为当前脚本、PC 和变量状态的摘要；新的选项点与已展开的状态键相同时，该路线记为与先前路线合并，不再展开。
- **加速**：进入剧情后按住 `key.cfg` 中的普通跳过动作，与所选设备无关，并记入报告。跳过会在选项处自然停下。不加速时，《アマツツミ》共通线就需要约 5.4 亿步。
- **静默推进**：没有消息等待、没有候选选项、没有影片播放的状态持续 300 帧后，发出一次推进，用于"点击继续"一类的轮询循环；次数记入每条路线。
- **音频记录**：录制后端的请求日志有上限，会话每 100 帧换用新的录制后端；音频状态本身保存在核心宿主中。
- 外部启动脚本按虚拟机报告的脚本名登记，归档中的同名脚本不再重复计数。

## 15. 解锁轮次与汇总矩阵（2026-11-01）

实现 R4，并补充以下规则：

- **带存档运行**：R4 中每条路线从上一条路线留下的 `system.dat` 开始，相当于一名玩家依次游玩各路线；下一轮从上一轮结束时的系统存档开始。某一轮（第一轮除外）没有发现新的选项点、新的启用按钮、新的结束页面或新的起始页面形态时，判定收敛，结果为 pass L1。
- **按位置重放**：路线前缀记录每个选项出现的脚本和 PC，而不只是序号。系统存档变化后，如果选项出现在别处或记录的按钮不再可用，重放到此为止，该路线之后的部分按新探索处理，并在报告中记下偏离的深度。
- **所有入口**：起始页面上每个按钮都会测试，所有能进入消息等待的按钮都作为入口，各自展开一棵选项树。通关后新出现的标题按钮常常通向新剧情。
- **停止不中断轮次**：某条路线停止（闸门或未实现命令）时，其余路线可能仍会解锁内容，因此轮次继续进行；收敛后以第一条停止的路线作为 R4 的结果。
- 核心的 `Unhandled` 事件本身已包含加上 0x2000 的完整命令号，探针不再重复相加。

## 16. 完整实现（2026-11-01）

第 6 节检查清单中的全部检查均已实现，`--help` 由检查目录生成，逐行说明每个检查 ID。默认只运行几秒内完成的静态与启动检查（S1–S5、R1、D1）；其余检查要玩剧情或整条路线，需要在 `--checks` 中列出，`--checks all` 运行全部。

### 公共基础

- **剧情驱动器**（`scenario.rs`）：路线探索、存读档、输入和页面检查共用。它负责进入剧情、识别消息等待和选项、在无输入的轮询中静默推进，并在回到起始页面所在脚本、页面稳定时报告结束；另提供"在限定帧数内等待下一个事件"的接口，供可能没有反应的输入使用。
- **消息等待轨迹**：每个等待点记录当前脚本、PC 和最新回想条目的文字摘要。摘要只取条目中的字符串，不取状态字，因为打开回想会改写状态字。D2、I2、V1、V3 都比较这种轨迹。
- **键盘设备**：按钮按"下一个链接"（动作 3）逐个导航，直到目标成为当前按钮再确认；导航时引擎会移动指针，会话负责接收这次移动。《クロノクロック》上用键盘探索得到的选项树与鼠标完全相同。
- **原生对话框**：设置页中的字体按钮会打开系统字体对话框（0x213d）。探针模拟取消对话框的玩家：对每次对话框都预设"取消"，并记一条事件。
- **用户目录**：多个 Runner 共用同一个输出目录时，用户目录名不会重复，避免存档相互污染。

### 各族检查的判定方法

- **S4**：`data/` 下所有封包条目都要通过校验值，并按类型检查头部（PB3、Ogg、CMV6/8/9）；散放的音频和影片文件检查签名或索引。脚本引用的资源名大多在运行时拼出，静态解析不了，所以只检查资源本身。**S5**：游戏自带 `save/` 中的系统存档和剧情存档能被解码。
- **V1–V4**：在剧情第 30 个消息等待后、引擎已建好快照的第一个等待点存档，再记录随后 20 个等待。V1 在新会话中从标题读档，V3 在同一会话中读档，两者都必须走过同样的等待。读档后会先停在存档点那句话之前、重新显示这一句，所以允许读档后的轨迹在开头最多多出 2 个等待再对齐，报告中记录偏移量。V2：读档后立即再存，快照、脚本内存映像和辅助段必须逐字节相同，不同时报告第一个不同的快照记录标记。V4：覆盖槽位时引擎必须把旧版本留在 999 号槽，读档前的状态必须留在 998 号槽，各槽存档头都能解析。**V5**：通关一条路线后，以它留下的系统存档重启，起始页面必须与路线结束时的页面相同。
- **D2/I2**：16 ms 与 33 ms 帧时间、鼠标与键盘分别跑剧情开头 40 个等待并比较轨迹。不一致时，报告会区分"某一方在某处多停了一次、其余一致"和"轨迹无法重新对齐"。**D3**：损坏或截断的系统存档、缺失或损坏的剧情存档都必须被干净地拒绝或回退，不能崩溃（以捕获 panic 判定）或卡死（以步数上限判定）。
- **I1**：在第 10 个等待处逐个执行推进、取消、滚轮上/下、按住跳过，记录各自的效果。动作后先运行90帧，再直接观察等待或稳定页面，不调用剧情选择驱动器；回想等页面可以同时有多个控件组。**I3**：取消一次再取消一次，画面和等待点必须复原；按住跳过再松开后，剧情必须重新等待输入。**I4**：滚轮上打开回想，先用取消、再用滚轮下关闭，必须回到原来的等待点；先用取消，是因为滚轮下可能同时绑定了推进。**I5**：固定种子的随机输入跑 3000 帧，只有错误或闸门停止才算失败。
- **R5**：用第一遍留下的系统存档再跑同一条路线，必须遇到同样的选项，且帧数不多于第一遍。**L1**：整条路线中每 500 帧采样场景对象、SE 声道、按钮组、序列和回想条数，末段最大值超过中段最大值 1.5 倍加余量的才算泄漏；回想这类早早达到上限的计数不会被误判。
- **P1–P3**：页面图的节点是稳定页面或剧情中的某个消息等待；每次尝试都从新会话重放到节点，再按一个按钮或取消键。节点身份只看脚本和各按钮组的槽位与按钮数，因为滑块位置和解锁状态会改变按钮坐标和启用状态。每页最多尝试 64 个按钮（更多时均匀抽样），每张图最多 400 次尝试，深度 3。P2 对每条"去—回"往返比较画面摘要，变量是否复原只记录、不作判定。P3 列出退出和返回标题的控件。**P4**：分别用游戏自带模板和通关一条路线后的系统存档建图，按（脚本、槽位、按钮数）比较按钮组；同槽位的按钮数减少，或同尺寸组的启用数减少，才算失败。
- **C1**：页面图中按下后玩家设置（文字、自动推进、已读跳过、音频混音）发生变化的控件。许多设置页在离开时才写入设置，所以对按完仍留在原页的控件，会再按一次取消离开后比较。**C2**：改变设置、退出设置页、按正常退出保存偏好，再以保存的 `system.dat` 和 `cmvs.cfg` 重启，设置必须保持。**C3**：找到改变文字速度的控件后，比较默认设置与改变后到第 10 个等待所需的帧数。**C4**：在设置页中寻找能把设置恢复原值的控件，包括再按一次同一个开关。找不到设置控件且页面图被闸门阻止时，C2–C4 报告该阻止原因。

### 选项文字与清单

- **选项文字**：选项出现时读取可见文本对象和辅助文字槽中的字形，按纵坐标分行，并按 Shift-JIS 解码。单字节字符以符号扩展存储（0xff00–0xffff），需要按一个字节处理。
- **清单**（`--manifest`）：每行一条指令，`--` 之后必须写证据，`#` 开始注释：

```text
profile <档案 ID>                                   -- <证据>
entry <按钮组> <按钮>                               -- <证据>
choice-group <脚本> <槽位>                          -- <证据>
label page <脚本> <槽位>x<按钮数>[+...] <文字>       -- <证据>
label choice <脚本> <PC> <文字>                     -- <证据>
```

  `entry` 覆盖自动找到的剧情入口；`choice-group` 只在同时出现多个候选组时生效；`label` 只影响报告中的可读名称。档案与识别结果不一致时探针拒绝运行。报告头列出每条指令是否被使用，以及清单与自动识别不一致之处。《アマツツミ》不需要任何纠正，审阅过的清单（只有标签）放在 [`docs/games/amatsutsumi/probe.manifest`](../games/amatsutsumi/probe.manifest)。

### 存档分叉

`--fork save` 让选项树的分支从检查点开始。遇到新的选项点时，用引擎存档功能写一个分叉存档；引擎保存的是最近一个剧情快照点（0x22b2）的状态，因此读档后会从该点重新走到选项。分支在新会话中预置该存档和当时的系统存档（解锁轮次中预置最新的系统存档），在标题读档后继续。遇到第一个选项时，在前缀中倒查同一位置来对齐深度，因为快照点与选项之间可能隔着更早的选项。缺少快照布局能力的构建自动退回重放。《アマツツミ》上分叉与重放得到相同的 4 条路线和选择路径，用时从 18 分钟降到 9 分钟，执行指令数仅多 131 条（读档本身的代码）。

release，帧时间 16 ms，种子 0，`--max-steps 800000000`（《クロノクロック》为 300000000）。《アマツツミ》的各项结果来自本节实现过程中最终代码的分项运行；《クロノクロック》来自一次 `--checks all --allow-presumed --allow-unreviewed`（17 分钟）。

由此发现及后续纠正的问题：

- **0x21fa 世界运动插值模式**与 **0x22ff** 未实现，挡住了《クロノクロック》的整条路线和设置页。
- **I4旧误判已纠正**：回想经回调返回时保留等待的repeat计数。原检查只认repeat=2的新等待，忽略已有等待，随后驱动器自行推进一句。返回检查现在接受repeat>=2的挂起0x2153；两款游戏的脚本/PC/文字摘要均保持，I4重跑通过L1，运行时未改。逐帧证据与报告见[研究记录](../games/chronoclock/research.md#2026-11-01存档分叉验证与回想检查纠正)。
- **D2旧误判已纠正**：300帧兜底确认在16ms下提前结束活动定时序列，33ms下序列已自然结束。场景驱动器现将活动序列视作执行进展，重置空闲计数，避免注入该确认；本作16/33ms前40个等待重跑一致，两款游戏D2均通过L1。运行时未改，见[证据](../games/chronoclock/research.md#2026-11-01d2定时序列误推进纠正)。
- 《クロノクロック》通关后新出现的两个标题按钮分别进入 `hscene.ps3` 和 `omake.ps3`，3600 帧内都没有出现稳定页面，诊断信息已写入勘察结果。

选项文字可以正确读出，例如《アマツツミ》的「こころを愛している／まだ迷っている」「殺してやる／…………」，以及《クロノクロック》的「美咲は恋愛対象ではない／美咲が好きだ」。

### 第 12 节问题的结论

1. 分叉：重放与存档分叉都已实现，默认重放，`--fork save` 可选；内存快照不再需要。
2. 清单位置：`docs/games/<游戏标识>/probe.manifest`，行格式如上，只含引擎层词汇和证据。
3. 选项识别：在两款游戏上都只靠自动识别，未出现多候选组；`choice-group` 留作纠正手段。
4. 摘要排除字段：等待点轨迹只比较脚本、PC 和回想字符串，已足以支撑 L1 检查；整状态摘要仍只用于同一构建的确定性比较。
5. L2 参考包：仍需另行设计原版采集方法。
6. 预算：单会话步数上限默认 5000 万，整条路线需要 `--max-steps 800000000`；每棵树 16 条路线、4 轮解锁、每张页面图 400 次尝试。
