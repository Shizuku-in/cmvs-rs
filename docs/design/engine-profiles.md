> 状态：**已确认；P1、P2 已实现**（P1见第12节，2026-10-31的P2见第13节）。起草基线 `15c9fa4`，第11节的决定2026-10-30确认。当前行为见[架构](../architecture.md#引擎档案与命令闸门)，本文保留决策记录。

## 1. 要解决的问题

现在的命令语义只有一套，实际默认对所有游戏生效：

- 系统命令按"责任链"分派：`runner::Startup::step_once` 依次调用各宿主的 `try_handle`，每个宿主自己判断命令号。`cmvs-trace` 另有一条独立的链。两条链都没有"当前是哪个引擎"的概念。
- 核心代码注释里有 585 处原版地址（57 个文件），全部指向《アマツツミ》的 `cmvs64.exe`。研究约定要求"地址与二进制哈希绑定"，但运行时并不检查。
- `runner.rs` 写死了 `data/pack/start.ps3`、`data/pack/script.cpz`、本作游戏 ID `0x17800016` 和变量 2198（`--skip-auto-resume`）。
- 2026-10-30 的 CHRONOCLOCK 摸底中，trace 用《アマツツミ》的语义跑了 43076 步，没有任何提示（见[档案](../games/chronoclock/README.md)）。

"处理函数"指不指向空操作存根的 case；"比基准少/多"是与《アマツツミ》x64 按 case 号比较处理函数集合的结果。

**P1 实现时的更正**：普查最初把"出现最多的跳转目标"当成 default，实际上那是一个共用的空操作存根（`mov eax, 0x4000` 后直接返回，不回收参数、没有副作用）。真正的 default 是 `ja` 的目标（返回 0），32 个 exe 中没有任何范围内的 case 指向它，只有越界命令会走到。所以表中"处理函数"的数字不变，但"比基准少"的命令在旧构建里是**空操作**，不是"不存在"。存根在各时代有 5 种字节形态（x64 一种，x86 四种），P1 按字节精确识别。

**结论**

1. **分派结构 16 年不变。** x64 都是 `movzx eax, dx` 后接 switch；x86 都是 `cmp` 后接 `jmp [reg*4+table]`。只有表的大小在增长：800 → 864 → 928 → 976 → 992。
2. **处理函数集合单调增长。** 早于基准的引擎，处理函数集合全部是基准的子集；晚于基准的，全部是超集。没有出现过删除或重编号，这是"命令号跨版本稳定"的强证据，但**不是**语义不变的证据。旧构建中缺少的处理函数都是空操作（见上文更正），套用基准语义同样是错的。
3. **同一构建的 x86 与 x64 一致。** 13 对 exe（两款 RE 共用同一对）的命令集合完全相同；PE 时间戳不完全相同，但每对只相差 66–147 秒，应是同一份源码先后连续编译的结果。
4. **6 款游戏只有 x86 exe（2007–2010），而每款游戏都有 x86 exe。**草案原先的"只做 x64 档案"不成立。
5. **编译器分四个时代**：VS2005（8.0）、VS2008（9.0）、VS2010（10.0）、VS2015+（14.0）。同一份源码换编译器后机器码会大幅变化，这直接限制了指纹继承（见第 7 节）。2019 年后 x86 exe 从约 1.7 MB 缩到约 1.06 MB，与换编译器同时发生，没有加壳。
6. **封包有 4 代**：CPZ3、CPZ5、CPZ6、CPZ7。封包代际**与引擎构建无关**：2023 年的两款 RE 用 2022 年的引擎，配的却是 CPZ5。
7. **脚本容器统一。** 启动脚本扩展名在 2013 年由 `.ps2` 改为 `.ps3`，但都是 PS2A，头部布局相同。19 个启动脚本全部通过现有 PS2A 解码与字节码结构检查。启动脚本体量小，不能据此推断全部字节码分支都一致；全量脚本要等 CPZ3/5/7 能读后才能检查。
8. **一个构建可服务多款游戏。** 两款 2023 RE 的 exe 逐字节相同。

### 2.1 前代与其他引擎（同日补充）

用户另提供了 CVNS 4 款、PVNS 1 款、SIA System 1 款。普查方法同上，`.rar` 未打开。

| 引擎 | 样本 | exe | 链接器 | 最大 switch | 数据签名 |
|---|---|---|---|---|---|
| SIA System | 2000-09 天使達の午後（1 款） | `1055.exe` x86，约 12 MB | 6.0 | 未找到 ≥200 项 | `.pac`/`.chr`/`.msk`/`.pmp` 无统一签名，`.wav` |
| PVNS | 夏恋 -karen-（1 款，exe 为 2003-12） | `pvns.exe` x86 | 7.10 | 238 | `PBZ1`（`.pbz`）、`PSBP`（`.psb`）、`KAS1` 存档、`JMV2` 影片 |
| CVNS | 2004-06、2004-08、2005-08、2009-05（あるみ箱含两个独立游戏） | `cvns.exe` x86 | 7.10 → 9.0 | 544 → 608；2009 版的模式未命中 | `CPZ1` → `CPZ2`、`PSS0` 脚本、`CSS0` 系统存档、`CMV3` 影片、`.cur` |

**结论**

1. **CVNS 与 CMVS 明显同源。** 封包从 `CPZ1/2` 延续到 `CPZ3/5/6/7`，系统存档从 `CSS0` 到 `CSS1`，影片从 `CMV3` 到 `CMV6/8/9`。CVNS 的 `PSS0` 头部与 PS2A 是同一个 12 字段布局，只是第 3、4 个字段（PS2A 的变换参数）为 0。两者在工具上也有交叉：2007 年的 CMVS 游戏带 `cvnsInst.exe`，2009 年的 CVNS 游戏带 `cmvsCheck.exe`。
2. **但 CVNS 的脚本载荷与 PS2A 不同。** 把 5 个 `start.pss` 的签名改为 PS2A 后，现有解码器都报"LZSS reference exceeds declared size"（只在 scratchpad 副本上试验）。字节码与 VM 是否兼容尚未确认，这是将来支持 CVNS 的关键问题。
3. **PVNS 可能是更早的前身**：命名风格相近（`PSB`/`PBZ`），但签名体系不同，只有 1 个样本。
4. **SIA System 与 CMVS 系没有共同格式**：没有 CPZ/PS 系签名，也找不到同形态的分派表。这是另一套引擎，不在 cmvs-rs 的范围内。

对本设计的影响：档案增加一个 `family` 字段（`Cmvs`/`Cvns`，以后可能有 `Pvns`），格式识别按家族分别处理。命令状态、闸门和指纹方法对 CVNS 同样适用，前提是它的系统命令也是 switch 分派（544/608 项的 switch 是候选，尚未确认）。

### 2.2 补充核对

再次确认：CHRONOCLOCK 的 712 个命令全部包含在基准中；`0x2026` 在两边都存在，粗比处理函数相同。静态提取的基准 `0x20d4 → 0x140074b10`、`0x22b3 → 0x14007c9e0` 与 VM 语义文档的记录一致。粗比方法见第 7 节的局限说明。

## 3. 目标与非目标

**目标**

1. 每次运行都明确选定一个引擎档案。选不出来就报错，不默认。
2. 区分命令**不存在于该引擎**、存在但**未复核**、经指纹**继承**、已**复核**、**基准**本身，以及**变体**。
3. 让新版本的复核量正比于"差异"，而不是正比于"命令总数"。
4. 允许只有游戏数据、没有 exe 时也能识别（移动平台的前提）。
5. x86 与 x64 都能作为证据来源。

**非目标**

- 不按版本拆 crate。CMVS 是一个引擎的多个版本，共用一套核心。
- 不改变任何现有命令的语义或宿主结构。
- 不在本草案中实现 CPZ3/5/7（第 8 节只定接口位置和优先级）。
- 不自动猜档案，也不用标题字符串当身份。
- 不支持 SIA System 等与 CMVS 不同源的引擎。CVNS/PVNS 只预留 `family` 字段，不在本草案中实现。

## 4. 核心概念

### 4.1 引擎档案（`EngineProfile`）

**一个构建对应一个档案。**同一构建的 x86 和 x64 exe 合为一个档案，各自登记二进制身份。档案是语义来源，与游戏无关；多款游戏共用一个构建时，就共用一个档案。

| 字段 | 说明 |
|---|---|
| `id` | 稳定 ASCII 标识，用家族加构建日期，与游戏无关，如 `cmvs-20160201`（《アマツツミ》）、`cmvs-20150405`（CHRONOCLOCK）。同日有多个构建时加哈希前缀 |
| `family` | `Cmvs`；将来可能有 `Cvns`。决定格式识别和脚本容器的分支，不同家族之间不做指纹继承 |
| `build` | 各 exe 的 PE 时间戳与链接器版本 |
| `binaries` | 每个架构一项：文件名、SHA-256、image base、分派表 RVA、switch 项数。地址只对所属的那一项有效 |
| `base` | 基准档案 `id`。根档案为空 |
| `commands` | 命令表，见 4.3，长度等于该构建的 switch 项数 |

**同构建判定**：同一游戏目录中的 x86 与 x64 exe，PE 时间戳相差不超过 5 分钟（普查实测 66–147 秒）且命令集合相同，才合并为一个档案。档案中记录两个时间戳和这条证据。这个判定是推断：源码完全一致无法从 exe 直接证明，所以基准以外的档案仍要靠同架构指纹或人工复核获得语义。语义研究只需在其中一个架构上完成；另一个架构的地址仍要单独登记。

### 4.2 游戏记录（`GameRecord`）

把游戏数据映射到档案。**运行时依据数据识别，exe 只作佐证。**

| 字段 | 说明 |
|---|---|
| `game` | 游戏标识，与 `docs/games/<标识>/` 一致 |
| `profile` | 档案 `id` |
| `start_script` | 包外启动脚本的相对路径与 SHA-256：`data/pack/start.ps2` 或 `start.ps3` |
| `script_archive` | 脚本包的相对路径与 SHA-256 |
| `game_id` | 启动脚本交给 `0x201d` 的值，如《アマツツミ》`0x17800016`、CHRONOCLOCK `0x17700011` |
| `executables` | 已知配套 exe（`cmvs.exe`/`cmvs32.exe`/`cmvs64.exe`）的 SHA-256，可为空。同一游戏有多个补丁版本时分别登记 |
| `policies` | 本作专属的预览策略参数，如 `--skip-auto-resume` 用到的变量 2198 |

### 4.3 命令状态（`CommandStatus`）

| 状态 | 含义 | 运行时行为 |
|---|---|---|
| `Absent` | switch 的 default（返回 0），以及超出该构建项数的命令 | 总是报错，研究参数也不能放行 |
| `NoOp` | 指向共用空操作存根：返回 0x4000，无副作用 | 总是报错（这一行为尚未实现）；`--allow-unreviewed` 不放行，因为套用基准语义是错的 |
| `Base` | 仅根档案使用：语义来源就是这个构建 | 进入现有分派链；Rust 未实现时仍报现有的 `Unhandled` |
| `Inherited { fingerprint }` | 同架构的处理函数指纹与基准相同，继承基准语义 | 同 `Base`；日志计数里单独统计 |
| `Reviewed { note }` | 指纹不同，但已人工复核，确认与基准语义一致 | 同 `Base` |
| `ContractEquivalent` | 有效登记证明下，两侧完整契约一致 | 进入已有处理器；按来源统计尝试，证明过期/撤销时 Registry 拒绝加载 |
| `Presumed` | 旧指纹的可比较部分相同，但依赖不完整 | 默认停止，仅显式 `--allow-presumed` 研究放行 |
| `Variant(VariantId)` | 已复核，语义与基准不同 | 交给知道这个变体的宿主；宿主不认识就报错 |
| `Unreviewed` | 有处理函数，但尚未比对、比对后不同，或基准中没有 | 默认报错；`--allow-unreviewed` 放行，每个命令首次放行时记录一次 |

P1 实现了 `Absent`、`NoOp`、`Base`、`Unreviewed`；P2增加带强制证据的 `Inherited`。`Reviewed`、`Variant` 留待P3，不把指纹不完整的命令当作已人工复核。

"命令状态"表示档案对这个命令知道多少；"Rust 是否实现"仍由分派链决定。两者正交，不合并。

## 5. 选择流程

```text
输入：游戏根目录，可选 --profile <id>
1. 找到包外启动脚本（data/pack/start.ps3，没有则 start.ps2）和脚本包，计算 SHA-256，查 GameRecord
2. 对根目录存在的 cmvs.exe / cmvs32.exe / cmvs64.exe 计算 SHA-256，与记录的 executables 比对
3. 判定：
   --profile 已给出            → 用它；basis = Explicit，第 1、2 步的结果只记入证据
   记录命中、exe 命中或不存在   → basis = Data(+Binary)
   记录命中、exe 存在但未知     → 报错 UnknownBinary（可能是未登记的补丁），提示 --profile
   记录未命中                   → 报错 UnknownGame，附带全部证据
4. 运行中执行 0x201d 时，若 record.game_id 与实参不同 → 报错 GameIdMismatch
```

结果类型：

```rust
pub struct ProfileSelection {
    pub profile: &'static EngineProfile,
    pub record: Option<&'static GameRecord>,
    pub basis: SelectionBasis, // Explicit | Data | DataAndBinary
    pub evidence: Vec<String>, // 例如 "script.cpz sha256 aa4bd891… matches chronoclock"
}
```

trace 和桌面在启动时打印选择结果和证据。trace 用 `#` 开头的注释行打印，便于把基线回归日志与旧日志逐行对比。

哈希成本：每次启动要读最多三个 1–2 MB 的 exe 和一个数 MB 的脚本包，可以接受。不哈希 GB 级的资源包。

## 6. 代码集成

### 6.1 新模块

- `cmvs-core::digest`：自写 SHA-256，保持 core 无依赖，用 FIPS 180-4 标准向量测试（合成数据）。
- `cmvs-core::profile`：定义类型、内嵌表、解析、查询，以及基于 `std::fs` 只读的选择函数。

### 6.2 表的存放

档案表是生成的元数据（命令号、各架构的处理函数 RVA、状态、指纹哈希），不含原版代码字节。推荐方案：

- 放在 `crates/cmvs-core/profiles/<id>.profile`（游戏记录在 `games.txt`），用 `include_str!` 内嵌，启动时严格解析。表由 `cmvs-profile table` 生成，状态只在复核后手改。
- 解析时检查：行数等于声明的 switch 项数且从 `0x2000` 连续；同一行的各架构必须同为处理函数、同为空操作或同为 default；各 exe 的时间戳相差不超过 5 分钟；状态与 case 类型和档案类型相符；派生档案的基准必须是同家族的根档案；游戏记录引用的档案存在，且记录的 exe 都是该档案的二进制。

实际格式（P1）：每行一个命令，先状态，再按 `binary` 行的顺序给出各架构的 case 入口 RVA，default 写 `-`。P2 再增加指纹列。

```text
profile cmvs-20150405
family cmvs
base cmvs-20160201
binary x64 file=cmvs64.exe sha256=d1c4…911d timestamp=0x55219bdb linker=10.0 image-base=0x140000000 table=0x81344 default=0x7eaba cases=976
binary x86 file=cmvs32.exe sha256=30ed…49b4 timestamp=0x55219b5a linker=10.0 image-base=0x400000 table=0x72aac default=0x70c62 cases=976
0x2026 unreviewed 0x7ed2f 0x70dc4
0x211e noop 0x7eaa7 0x70c53
```

### 6.3 分派闸门

在 `Step::System` 之后、进入分派链之前，调用同一个函数：

```rust
// runner::Startup::step_once 和 cmvs-trace 共用
profile::check_command(selection, pc, command, allow_unreviewed)?;
```

- 宿主代码在第一阶段不改。
- runner 和 trace 两条分派链目前有重复，闸门必须是同一个函数，避免两边行为漂移。合并两条链不在本草案范围内。
- 闸门的位置放在现有 `0x129` 写入和等待分支之前；具体顺序在实现时对照两条链确认，原则是不改变《アマツツミ》的现有执行顺序。

### 6.4 变体

等出现第一个真正的 `Variant` 时，再给相关宿主的 `try_handle` 加 `&EngineProfile` 参数。现在没有已知变体，不预先改签名。

### 6.5 写死的本作常量

## 7. 指纹工具

分为两步：导出依赖 IDA，比较只依赖 Python 标准库，结果可复现。

1. **导出**：`tools/ida_export_commands.py`（IDAPython）。支持 x64 和 x86 两种分派形态：先定位 switch，再对每个命令跟随 case 存根找到真正的处理函数，导出归一化的指令流。
2. **比较**：`tools/profile_compare.py`（`python -I`，仅标准库）。输入两份同架构的导出，输出档案 TSV。

**归一化规则（保守：宁可多报"不同"，也不能误报"相同"）**

- 保留助记符、寄存器、立即数和结构体偏移。对象布局一变，指纹就会变，这是期望的行为。
- 直接 call/jmp 的目标替换为被调函数的指纹，递归到固定深度并处理环。导入函数用导入名代替。
- 数据引用（x64 的 RIP 相对地址、x86 的绝对地址及重定位项）替换为占位符。若目标在只读节，把被引用的数据字节并入指纹。
- 超过深度上限的被调函数标记为"截断"，截断的指纹不能产生 `Inherited`。

**状态判定**（只在同架构之间比较，x86 指纹与 x64 指纹从不互比）

| 基准 | 派生 | 结果 |
|---|---|---|
| 有处理函数 | 空操作或 default | `NoOp` / `Absent` |
| 存在 | 存在，指纹相同且未截断 | `Inherited` |
| 存在 | 存在，指纹不同或截断 | `Unreviewed`，待人工复核后改为 `Reviewed` 或 `Variant` |
| 不存在 | 存在 | `Unreviewed`（基准没有这条语义可继承） |

**跨架构**：只有 x86 的老游戏（2007–2010），与基准构建的 x86 exe 比较。基准 x86 与 x64 的语义一致性由 4.1 的同构建判定担保。

**跨编译器时代**：同一份源码换编译器后，指纹大多会不同，所以继承只在同一编译器时代内有效。基准处于 VS2010 时代（2013–2017，共 5 款）。对其他三个时代的建议是"时代锚点"：每个时代选一个构建做人工深度复核，成为该时代的二级基准，时代内的其他构建再对锚点做指纹继承。这样全系列需要深度复核的是约 4 个构建，而不是 19 个。锚点之间如何高效对照（例如在反编译伪代码层面做归一化比较）是待研究的问题。

**局限**：`Inherited` 不等于验证通过。启动时在别处初始化的全局表、深度截断以外的行为，都可能藏着差异。所以运行日志要分别统计 `Base`、`Inherited`、`Reviewed` 三类命令的执行次数，出问题时能回溯。第 2 节的粗比只看每个处理函数的前 0x80 字节、只屏蔽了 `E8`/`E9` 偏移，只能说明方法可行，不能当作继承依据。

## 8. 格式层

- 格式代际按文件签名识别，**与档案无关**。档案和游戏记录只登记预期格式，用于一致性检查。普查已证实两者独立（2022 年构建配 CPZ5）。
- 已确认需要支持的封包有 4 代。按普查覆盖面排序：CPZ5（11 款，含两款 RE）、CPZ7（4 款）、CPZ6（2 款，已支持）、CPZ3（2 款）。主线仍是《アマツツミ》；排期时可按这个顺序考虑。

- PS2A 容器目前看是统一的，不需要分代；若全量脚本检查发现字节码差异，再按构建登记。
- 识别工具会打印逐项证据，例如"`script.cpz` magic=CPZ5"、"`start.ps2` PS2A"，在摸底时一眼看出格式代际。它也识别 `cvns.exe`/`PSS0`/`CPZ1`/`CPZ2` 等前代特征，报告为"CVNS 家族，未支持"，而不是笼统的"未知游戏"。

## 13. P2 实施与使用（2026-10-31）

语义基线`8eb8708`。本阶段只改工具、档案元数据和闸门，不新增命令语义。前期越过P2实施的可见性、模式65和字节计数作为独立研究保留；后续先复核默认停点`0x201f`，暂停沿研究放行路径追`0x2112`。

### 导出与保守边界

`tools/ida_export_commands.py`使用IDA 9.4的解码/函数边界接口，不需要Hex-Rays。只读校验原exe SHA-256与数据库输入身份、拒绝补丁字节，独立定位唯一switch并逐项核对档案的case入口。导出必须在原游戏目录之外。批处理只能对`local/`中的数据库副本或新建分析库运行；不要对原目录数据库执行批处理退出/保存。

导出包含从每个case入口可达的指令、入口索引、局部分支/顺序边、调用依赖和只读数据。指令保留原编码中的寄存器、立即数和字段偏移，仅将已识别的控制/数据地址字段置零并附语义引用。内部目标变为指令索引，外部直接调用/尾跳变为被调函数指纹，导入保留模块和符号名。只读标量附完整已知数据项及偏移，读取越过项边界、取地址、索引读取、可写/未知数据、数据重定位、间接控制流、缺失解码均使整条依赖链不完整。

`tools/profile_compare.py`仅依赖Python标准库。同架构、同策略比较；默认递归深度8，循环或深度截断均保留`Unreviewed`，不凭相同的“不完整”标记继承。这比第7节的目标更保守：尚未证明安全的数据引用不会仅替换成占位符就继承。函数入口与控制流也纳入指纹，避免只因可达指令集合相同而误判。

导出含原指令字节，仅留忽略的`local/`；Git只保存档案中的哈希与[两份比较报告](../games/chronoclock/profiles/)。`python -I tools/test_profile_compare.py`使用合成函数图验证调用依赖变化、常量/寄存器/偏移、数据/导入差异、入口/CFG、截断/环、跨架构及身份绑定。

### 操作示例

在已打开且匹配档案的IDA会话中导入模块，调用：

```python
export_commands(".../cmvs-20160201.profile", ".../local/base-x64.json")
```

也可用`idat -A -S".../ida_export_commands.py PROFILE OUTPUT.json" LOCAL_COPY.i64`导出本地数据库副本；新建分析库时显式用`-o`指定`local/`目标。先分别导出基准与派生构建的同架构数据，再比较：

```powershell
py -3 -I tools/profile_compare.py local/base-x64.json local/derived-x64.json --report local/comparison-x64.tsv --base-profile crates/cmvs-core/profiles/cmvs-20160201.profile --profile crates/cmvs-core/profiles/cmvs-20150405.profile --output-profile local/derived.profile
py -3 -I tools/profile_compare.py local/base-x86.json local/derived-x86.json --report local/comparison-x86.tsv
```

比较工具不覆盖输入；候选档案经Rust解析/Registry验证后再纳入仓库。不能把x86指纹与x64指纹互比，也不直接合并两份报告。本轮以x64为档案证据；x86的差异/截断不是语义差异证明，保留独立核对范围。

### 档案与运行

证据架构在`binary`行之后各声明一次根exe，`inherited`行在各架构case RVA之后只给出完整指纹：

```text
inherit <arch> base-sha256=<base-exe-sha256>
0x2000 inherited 0x7ea86 0x70c36 inherit=<arch>:<complete-fingerprint>
```

派生exe即本档案同架构`binary`行的SHA-256，不再逐行重复。每个`inherit`头部行必须有对应架构的`binary`行、同架构不得重复，且至少被一条`inherited`行使用；没有头部行的架构不能给出证明。Rust以`InheritanceProof`独立保存证据，`CommandStatus::Inherited`表示分类；解析时禁止无证据继承或给其他状态加证明，验证派生exe及同架构根exe的SHA-256、根命令状态和档案家族。闸门允许`Inherited`进入现有分派，未实现的Rust命令仍会显式停止。

`cmvs-profile identify/show`分别列出Base/Inherited/Unreviewed/NoOp/Absent。`CommandGate::counts`分别统计已放行的Base/Inherited/Unreviewed分派尝试；等待重试会再计数，明确不称为完成指令数或覆盖率。trace在派生档案停止时打印此统计，runner亦暴露同一统计API。根档案日志不增加新行，保持逐字节回归。

CHRONOCLOCK默认trace在首条`0x201e`后进入`0x201f`，后者因可写全局依赖未继承；统计为Base=0、Inherited=1、Unreviewed=0。基准与P2使用相同种子0/16ms、同一CSS1副本、百万步预算的121639651字节日志完全一致，两边均以预算耗尽退出码1。具体输入身份、输出哈希及检查结果见[CHRONOCLOCK研究记录](../games/chronoclock/research.md)。

## 14. 指纹策略 v2（2026-10-31）

策略名 `raw-operands-closed-cfg-readonly-data-libraries-v2`，导出格式 `cmvs-command-graph-v2`。两边必须使用同一策略，v1 导出不能与 v2 比较。

### 动机

v1 报告中 325 条未复核命令只有 10 条完整指纹不同。逐个函数分类阻断原因后发现，多数命令卡在同一批函数上：IDA 用库签名（FLIRT）识别出的静态链接运行库。例如带栈保护的函数都会到达 `__report_gsfailure`（200 条命令），`operator new` 会经 `_callnewh`、`doexit` 等到达运行库内部（170 条）。运行库内部的间接调用、可写全局和未解码指令使这些命令永远不完整。

另一类是 IDA 为栈上结构体成员记录的"数据引用"：目标是类型 ID（如 `0xff000000000035f4`），不在任何段内，并不是内存访问，却被 v1 记为 `unmodeled-data-reference`。

### 规则

1. **运行库叶子**：带 `FUNC_LIB` 标志、从函数入口进入、且有稳定名称的函数作为叶子导出。指纹由库名与自身归一化代码决定；其中的局部分支照常保留，被调函数与数据引用置为不透明占位，不再展开，也不报告数据和间接流问题。叶子自身的解码问题仍会阻止继承。
2. **名称必须稳定**：IDA 的占位名（`sub_`、`nullsub_`、`j_`、`unknown_libname_` 后接编号或地址）由数据库自行生成，不能跨构建作为身份；导出时这类函数按普通函数展开，比较工具也拒绝以它们为库名。重名后缀（如 `_0`）由自身代码哈希兜底。
3. **段外引用**：`DataRefsFrom` 中不属于任何段的目标不再记为未建模数据引用。段内未被操作数解释的引用仍然阻止继承。

这是一条显式的信任边界，与导入函数按"模块!名称"比较同理：两个构建若链接了同名且自身代码相同的运行库函数，就认为其行为一致。运行库被调函数之间的差异不会被发现；如果将来遇到不同编译器时代的构建，需要重新评估这条边界（两者当前同为 VS2010）。

### 结果

CHRONOCLOCK 对基准，同一参数（深度 8）：

| 架构 | v1 继承 | v2 继承 | v1 继承在 v2 中丢失 | v2 完整但不同 |
|---|---|---|---|---|
| x64（档案采用） | 387 | 434 | 0 | 12 |
| x86（独立核对） | 362 | 415 | 0 | 未单列 |

x86 继承的命令在 x64 中全部继承；只在 x64 继承的 19 条在 x86 上都是不完整（间接流或数据），没有一条判为不同。x64 两边各有 35 个运行库叶子。档案中 3 条已继承命令因指纹树改以库叶子结尾而更新指纹，状态不变；人工复核的 `0x201f` 原样保留，v2 报告仍判它不完整。

CHRONOCLOCK 默认 trace 停点仍是 `start.ps3 / 0x50 / 0x2091`：它卡在可写全局，v2 未处理。余下未复核原因（可多选）：可写或未解析数据 205、间接控制流 154、未解码指令与缺失顺序后继各 110、递归环 68、段内未建模引用 68、深度截断 37、完整但不同 12。

### 下一步的边界

v1 报告的模拟显示，可写全局若能配对，上限可再解锁约 30 条命令。但同一次统计表明，`.data` 中只被直接访问的全局有六成以上紧挨着被取地址的对象（距离 0x100 字节以内）。IDA 的数据项边界不等于 C 对象边界，通过相邻对象指针的访问无法从交叉引用看出，所以全局配对需要另行设计其保守边界，不在 v2 中做。

### 复核辅助 `--explain`

`profile_compare.py BASE.json DERIVED.json --explain <opcode>` 只读两份导出，不写文件、不改变任何状态，输出一条命令为何没有继承：逐层列出两边配对的函数（`same`、`different` 或不完整原因），阻断继承的指令（函数内偏移、归一化字节、原因），第一处不同的指令，以及被阻断数据引用在两边的地址和原因（`writable`、`address-taken`、`indexed`、`undefined` 等）。被调函数和数据只在相同的指令前缀内按位置配对。

为此导出增加了仅供诊断的字段：指令的函数内偏移与所触发的问题、未解码位置、被阻断数据引用的目标与原因。指纹只使用 `bytes`、`refs`（不含被阻断的数据引用）和 `next`，库叶子同样只取这三项。用带诊断字段的新导出重新比较，x64 报告除头部的导出哈希外逐行相同，434 条指纹不变。

首次用于 `0x2091` 即发现一处未建模引用：`lea reg, [rip+…]` 取映像基址（`0x140000000`，PE 头不在任何段内），位移未置零也未报告，函数位置一变就判为不同。它只会造成误报"不同"，不会误判相同；与映像基址相对的表访问一起留到下一轮工具改进。

## 15. 指纹策略 v3 与 `Presumed`（2026-10-31）

策略 `raw-operands-closed-cfg-readonly-data-libraries-switches-v3`，导出格式 `cmvs-command-graph-v3`。

### 导出规则

1. **switch**：IDA 识别的 switch 跳转导出"case 值 → 局部目标"的映射和默认目标，映射参与指纹；跳转表与索引表的引用记为 `switch-table`，不再算间接控制流或数据阻断。
2. **映像基址**：`lea reg, [映像基址]` 记为 `image-base`。
3. **映像相对位移**：x64 的 `[reg+reg*n+RVA]` 只在两种情况下解释为映像相对引用：IDA 给出了对应的数据引用；或在同一基本块内，此前有 `lea reg, [映像基址]` 写入它的基址或索引寄存器，且之后未被改写。向前扫描只跨越"唯一写入是目的操作数"的指令和条件跳转，遇到跳转目标、调用、字节寄存器写入或其他指令即停止。解释后按普通数据规则处理（索引访问仍阻断内容），位移置零。结构体字段偏移不满足这两条，保持原样参与比较。
4. **不返回调用**：被 IDA 标为不返回的函数调用，如果其后紧跟 `int3` 填充，不再要求顺序后继。

这些规则使两个 x64 导出中的未解码指令、缺失后继和未建模引用全部消失；x86 导出另余 4 处函数外顺序后继和 2 处无法置零的引用编码。

### `Presumed`

条件：完整指纹不可用，阻断原因只属于"可写或未解析数据、间接控制流、递归环、深度截断"，并且两边的**形状指纹**相等。形状指纹与完整指纹的遍历相同，区别是：被阻断的数据引用记为不含地址的占位；回边记为"第几层祖先"；深度截断记为标记；每个函数的问题集合也纳入哈希。解码缺口、缺失后继、未建模引用、重定位数据等不在允许范围内，永远不会推定。

档案行写作 `presumed <各架构 RVA> presume=<arch>:<形状指纹>`。它与 `inherit=` 共用头部 `compare <arch> base-sha256=<根 exe>`；原来的 `inherit` 头部改名为 `compare`，因为它现在绑定两种机器证明。比较报告对形状不同的命令追加原因 `shape-different`，遍历超出预算时追加 `shape-limit`。重新生成档案时人工复核行保持不变。

闸门默认放行 `Presumed`，`GateCounts.presumed` 单独计数；trace 在派生档案停点列出已执行的推定命令（`# presumed commands run:`），运行出问题时优先排查它们。推定只说明"可比较的部分没有差异"，被阻断的部分仍可能藏着差异：可写全局在别处如何被写入、间接调用的实际去向、截断以下的代码。人工复核的证据等级高于推定。

### 结果

| 架构 | v2 继承 | v3 继承 | v3 推定 | v3 未复核 |
|---|---|---|---|---|
| x64（档案采用） | 434 | 455 | 168 | 89 |
| x86（独立核对） | 415 | 425 | 207 | 80 |

- v2 的继承在 v3 中全部保留。x64 剩余 89 条未复核命令都有可见差异：完整指纹不同 11 条，形状不同 78 条。
- 档案中：455 条 `Inherited`、167 条 `Presumed`、2 条 `Reviewed`、88 条 `Unreviewed`。人工复核的 `0x201f`（机器判定为推定）和 `0x2091`（机器判定为形状不同，首处差异是一处未证明的映像相对地址）保留复核行。
